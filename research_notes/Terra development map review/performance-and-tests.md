# Terra development map: performance, data loading and test coverage

All findings below are from reading code on disk at `/home/user/Terra` (commit `09457d1`, HEAD at time of review). Nothing here was profiled; where a cost is asserted it is a code-read claim about algorithmic shape, and I say so explicitly. "Sources" are file paths with line numbers, as this is a local-code review, not web research.

## How map data gets loaded: fetched, bundled or embedded? Does it grow without bound?

### Takeaway
Data is **fetched at runtime in two stages**: `market.json` carries only the "headline" projects for every metro, and the full list for the one metro being viewed is a separate `developments/<slug>.json` fetched on open. The headline set is capped per metro (300–400), but the **per-metro full file is uncapped** — it holds every collected TABS filing and city permit for that metro and grows with the dataset without bound.

### Cited findings
- The map is drawn from `data.projects` handed in by the view; nothing is embedded in the page — [`site/devmap.js:169`](site/devmap.js) `const all = cityProjects(data?.projects, city);`
- Two-stage load, documented in the loader's own comment: "market.json carries each market's biggest projects; the full list for the market being looked at is its own file, downloaded once on open. The map draws from the biggest ones meanwhile, and keeps them if the file fails." — [`site/markets-view.js:846-864`](site/markets-view.js)
- Stage 1 fetch: `fetch('market.json', { cache: 'no-cache' })` — [`site/app.js:880-885`](site/app.js). `cache: 'no-cache'` forces a revalidation round trip on every load even when the file is unchanged.
- Stage 2 fetch: `fetch(path, { cache: 'no-cache' })` where `path = data.files?.[city]` — [`site/markets-view.js:54-59`](site/markets-view.js), [`site/markets-view.js:851-853`](site/markets-view.js). Same `no-cache`.
- On arrival the full file **replaces** that city's rows in the shared snapshot and re-renders the whole section: `data.projects = [...data.projects.filter((p) => p.city !== city), ...file.projects]; devFiles.set(city, 'done'); render();` — [`site/markets-view.js:858-861`](site/markets-view.js). That means the entire `developmentMap()` card, its `drawList()` row set and its Leaflet map are built **twice** on every first open of a metro.
- Signed-in members read the same path from a Supabase `site_snapshots` row instead of the static file; the loader is swappable — [`site/markets-view.js:67-78`](site/markets-view.js), [`site/account.js:183`](site/account.js).
- Build side: `splitDevelopments()` puts only `p.headline` rows in `market.json` and writes one file per city with **all** of that city's projects — [`backend/src/market/devFiles.ts:65-77`](backend/src/market/devFiles.ts) (`headline: { ...result, projects: result.projects.filter((p) => p.headline) }`).
- The headline cap per metro: Houston 400, Dallas 400, Fort Worth 300, Austin 300, San Antonio 300, default 150 — [`backend/src/market/developments.ts:331-339`](backend/src/market/developments.ts). City permits add up to `CITY_MAX = 150` headline rows — [`backend/src/market/cityPermits.ts:33`](backend/src/market/cityPermits.ts), [`cityPermits.ts:757`](backend/src/market/cityPermits.ts).
- The full file has **no cap at all** — `splitDevelopments` groups by city and writes every project. The scale the build itself anticipates: "Harris County alone files about 4,000 a year" — [`backend/src/market/developments.ts:328-330`](backend/src/market/developments.ts).
- The check prints gzip sizes for `market.json` and the per-market file — [`backend/test/browser/devmap-check.mjs:673-694`](backend/test/browser/devmap-check.mjs) — so sizes are observable in CI logs, but as a printed table only (see the slow-phone section).

### Inferences
- The growth risk is entirely in the stage-2 file. Adding another two years of TABS history, or another permit city, inflates `developments/houston.json` linearly with no mechanism to stop it: no pagination, no viewport-scoped fetch, no field pruning. The `Development` row is wide (name, facility, scope, addresses[], permits[], parcels[], sourceIds[], aliases[], owner/tenant/contractor/designFirm, url, developerUrl) — see what `projectPanel` reads at [`site/devmap.js:1239-1251`](site/devmap.js) — so per-row bytes are high.
- `cache: 'no-cache'` on both fetches is a deliberate freshness choice but costs a full re-download whenever the ETag changes, which it does on every nightly build. A content-hashed filename plus `cache: 'default'` would make repeat visits free; this is the single cheapest data-loading win.
- The double render at [`markets-view.js:861`](site/markets-view.js) is the most expensive moment in the whole feature and is not measured separately anywhere: the first render builds N_headline rows + a Leaflet map, then it is thrown away and N_full rows + a second Leaflet map are built. Verified by reading `render()`'s path into `developmentMap()` at [`markets-view.js:789-797`](site/markets-view.js), which constructs a fresh `box` each time.

### Gaps
- I could not measure actual file sizes: `site/market.json` and `site/developments/` are build outputs and are not present in the checkout (`find . -name market.json` returns nothing). The real byte sizes are only visible in a CI run's printed table.

## Is list and pin rendering incremental or all-at-once? What breaks at 10x?

### Takeaway
The list is **partly incremental** (first 300 rows synchronously, the rest after a frame) and pins are **viewport-culled**, which are both real optimisations. But `drawList()` builds a DOM `<li>` for **every** project in the metro eagerly, before any filter is applied, and `api.show()` builds an O(N) string key on every filter change. Those two are the bottlenecks at 10x.

### Cited findings
- `FIRST_ROWS = 300` — "Rows put in the list before the first paint after a filter change." — [`site/devmap.js:97-98`](site/devmap.js)
- Incremental fill with a generation guard (commit `03dab75`, "Fill the rest of a long development list after the first paint"):
  ```js
  list.append(...rows.slice(0, FIRST_ROWS), empty);
  if (rows.length > FIRST_ROWS)
    requestAnimationFrame(() => setTimeout(() => {
      if (turn !== listTurn) return;
      const rest = document.createDocumentFragment();
      rest.append(...rows.slice(FIRST_ROWS));
      list.insertBefore(rest, empty);
    }, 0));
  ```
  — [`site/devmap.js:344-357`](site/devmap.js). The `turn !== listTurn` check correctly abandons a stale tail.
- Rows are **detached, not hidden**, on a filter change — "Only matching rows stay in the list: detaching costs far less than hiding thousands." — [`site/devmap.js:344-348`](site/devmap.js) (commit `ef25361`, "Keep only matching rows in the development list").
- **But every row is built up front, unconditionally**, before the first `apply()`: `const items = drawList(all, ...)` at [`site/devmap.js:319`](site/devmap.js), and `drawList` loops `for (const project of projects)` creating ~10 elements and 4 event listeners per project — [`site/devmap.js:1070-1106`](site/devmap.js). For N projects that is ~10N elements and 4N listeners created synchronously during card construction, whether or not they are ever shown. **This is the first thing that breaks at 10x.**
- Pin rendering is viewport-culled and incremental in effect: `const view = map.getPixelBounds().pad(0.5)` and `if (!view.contains(map.project(at, zoom))) return;` — [`site/devmap.js:871, 880, 934`](site/devmap.js). Markers are created lazily and cached: `pinFor()` with `pins`/`pills` caches — [`site/devmap.js:691-725`](site/devmap.js).
- Off-screen and overflowing projects are drawn as dots on **one canvas**, with the reason stated: "thousands of map layers would make filtering slow" — [`site/devmap.js:726-770`](site/devmap.js).
- `api.show(ids)` builds a per-project bitstring over **all** projects on every single filter/keystroke apply, purely as a change-detection key: `const key = projects.map((p) => (ids.has(p) ? 1 : 0)).join('');` — [`site/devmap.js:1014-1015`](site/devmap.js). At 40k projects that is a 40k-character string allocated and compared per keystroke. **Second bottleneck at 10x.**
- `apply()` runs `filterProjects(all, ...)` **three times** per invocation — for the list, for the legend counts (`off: []`), and for the chart (`since: ''`) — [`site/devmap.js:336-340`](site/devmap.js). Each is a full O(N) pass.
- `api.select()` does `shown.includes(project)` — a linear scan — [`site/devmap.js:1038`](site/devmap.js); and `step()` does `order.indexOf(selected)` — [`site/devmap.js:444`](site/devmap.js). Both O(N) per selection, called on every pin click and every next/prev press.
- `select()` iterates the **entire** `items` map on every selection to toggle one class: `for (const [p, item] of items) { const on = p === project; if (item.classList.contains('active') !== on) item.classList.toggle('active', on); }` — [`site/devmap.js:422-425`](site/devmap.js). O(N) DOM class reads per click. The `contains` guard avoids the write but not the read.
- `decorate()` does `speckPts.some((s) => s.p === project)` — linear over the speck array — on every hover — [`site/devmap.js:840`](site/devmap.js). Combined with `map.on('mousemove')` → `speckAt()` which is also a full linear scan of `speckPts` — [`site/devmap.js:771-789`](site/devmap.js) — this is per-mousemove O(specks) work on the main thread.

### Inferences
- Ranked bottlenecks at 10x (code-read, not profiled): (1) `drawList` eager row construction at [`devmap.js:319/1070`](site/devmap.js) — this is pure startup cost paid twice because of the stage-2 re-render; (2) the `projects.map(...).join('')` key at [`devmap.js:1014`](site/devmap.js); (3) the triple `filterProjects` at [`devmap.js:336-340`](site/devmap.js); (4) per-mousemove `speckAt`/`decorate` linear scans.
- Concrete fixes: build rows lazily (only for the rows about to be appended, memoised in `items`), replace the bitstring key with `shown.length` plus a cheap incrementing filter generation counter, derive the legend/chart sets from a single pass that records per-category and per-month tallies alongside the filtered array, keep `order` index in a `Map<project, number>` for `step()`, and track the active row in a variable instead of sweeping `items`.
- `speckAt` would want a coarse grid or quadtree only if specks reach tens of thousands; at today's 300–400 pins per metro it is irrelevant. This is the clearest example of a theoretical rather than measured problem.

## Clustering and fan-out: algorithmic cost, and is it recomputed more than necessary?

### Takeaway
Grid clustering has been **removed** — the current code is price-pill overlap packing below zoom 16 and exact-point fan-out at or above it. The pill packing is **O(k²)** in placed pills, and `draw()` is correctly rAF-coalesced on pan/zoom but is called **unconditionally and synchronously** from `api.select()`, i.e. on every pin and row click. Filter keystrokes are debounced at 120 ms.

### Cited findings
- The pill/speck split: `SPREAD_ZOOM = 16`, "Below this zoom projects are price pills (biggest first, never overlapping) and small specks; from it on, every project has its own icon." — [`site/devmap.js:631-632`](site/devmap.js)
- Overlap packing is a naive all-pairs test against every already-placed box:
  ```js
  const boxes = [];
  const free = (box) => boxes.every((b) => box[2] < b[0] || box[0] > b[2] || box[3] < b[1] || box[1] > b[3]);
  const order = [...shown].sort((a, b) => (b === chosen) - (a === chosen) || (b.cost ?? 0) - (a.cost ?? 0));
  ```
  — [`site/devmap.js:924-946`](site/devmap.js). Cost is O(k²) where k is pills accepted; the sort is O(N log N) and is **re-allocated and re-sorted on every draw**, i.e. on every pan and zoom, even though the cost order never changes except for `chosen`.
- Fan-out at high zoom: ring for ≤8 members, Archimedean spiral beyond — [`site/devmap.js:887-911`](site/devmap.js). Cost is O(m) per shared point, so O(N) total; bounded and fine.
- `CELL = 64` ("Cluster grid cell, in screen pixels") is still declared at [`site/devmap.js:633-634`](site/devmap.js) but **is never read anywhere in the file** — dead constant left from the clustering era (commit `ad2de4f` added clustering, `09457d1` replaced it with price pills).
- Likewise `clusterOf` is **dead state**: `let clusterOf = new Map();` at [`devmap.js:831-832`](site/devmap.js), `const nextCluster = new Map();` at [`devmap.js:874`](site/devmap.js) is never written to, and `clusterOf = nextCluster;` at [`devmap.js:954`](site/devmap.js) assigns an always-empty map that nothing reads. `node.dataset.clusters = '0'` is hardcoded at [`devmap.js:959`](site/devmap.js).
- Pan/zoom redraws **are** coalesced to one per frame: `const redraw = () => { cancelAnimationFrame(drawing); drawing = requestAnimationFrame(draw); }; map.on('zoomend moveend', redraw);` — [`site/devmap.js:963-968`](site/devmap.js). Note it is bound to `zoomend moveend`, not `move`, so there is no per-pixel work during a drag.
- Search is debounced at 120 ms, with the query stored immediately so a menu change inside the window cannot drop it — [`site/devmap.js:203-209`](site/devmap.js). Menu changes, legend clicks, chart clicks and sort clicks call `apply()` **undebounced** — [`devmap.js:231, 250, 398, 535`](site/devmap.js).
- `api.select()` calls the raw `draw()` twice-over synchronously, bypassing `redraw()`'s rAF coalescing — [`site/devmap.js:1040` and `1043`](site/devmap.js) — so a click pays a full pill repack inline.
- `fit()` also calls `draw()` directly after `fitBounds` — [`site/devmap.js:972-978`](site/devmap.js) — and `fit()` is reached from `api.show()` on every filter change [`devmap.js:1020`](site/devmap.js) and from the `ResizeObserver` [`devmap.js:980-987`](site/devmap.js).
- `fitBounds` builds a fresh `L.latLngBounds(shown.map((p) => where.get(p)))` over all shown projects on every filter change — [`site/devmap.js:974`](site/devmap.js) — another O(N) allocation per apply.

### Inferences
- The O(k²) packing is self-limiting in practice: k is bounded by how many non-overlapping pills fit on screen (a few dozen at phone size), not by N. So the pill loop's real cost is the O(N) `view.contains` rejection pass plus the O(N log N) sort — both linear-ish, and the sort is the removable part (precompute a cost-sorted array once, and handle `chosen` by hoisting it).
- Routing `api.select()` and `fit()` through `redraw()` instead of `draw()` would remove the one un-coalesced draw path left. Verified by code read; whether it is perceptible needs profiling.
- Removing `CELL`, `clusterOf`, `nextCluster` and the hardcoded `dataset.clusters` would delete dead code that the test still reads (`map.dataset.specks` is read where the variable is named `inClusters`/`clusters` at [`devmap-check.mjs:360-365`](backend/test/browser/devmap-check.mjs)) — the test's naming is now misleading in exactly the same way.

## Measurable main-thread work during interaction: layout thrash, repeated DOM queries in loops, sync reads after writes?

### Takeaway
There is real layout-read-after-write in the selection path and several repeated `querySelectorAll` sweeps per interaction, but no per-frame loop that reads geometry inside an iteration. The canvas speck painter does a forced resize + rescale on every paint, which is the most suspicious piece.

### Cited findings
- **Read-after-write in `select()`**: `panel.replaceChildren(...)` and `mapWrap.classList.add('panel-open')` are written at [`devmap.js:433-435`](site/devmap.js), then `mapWrap.getBoundingClientRect().top` is read at [`devmap.js:438`](site/devmap.js) — a forced synchronous layout after a large DOM write (the whole panel body). Earlier in the same function, `row.offsetTop`, `list.offsetTop`, `row.offsetHeight`, `list.scrollTop`, `list.clientHeight` are read at [`devmap.js:430-431`](site/devmap.js) immediately after `classList.toggle` writes across the whole `items` map at [`devmap.js:422-425`](site/devmap.js). Classic thrash shape, verified by code read.
- **Repeated DOM queries per interaction**: `select()` runs `list.querySelectorAll('.dev-pick[aria-current]')` plus a `node.closest()` per hit — [`devmap.js:428`](site/devmap.js); `close()` runs two more full `querySelectorAll` sweeps over the list — [`devmap.js:457-458`](site/devmap.js). On a 4,000-row list these walk the whole subtree on every open and close. A single remembered node reference removes all of them.
- `smallerHint`'s click handler re-queries `box.querySelector('.dev-smaller')` each time — [`devmap.js:260`](site/devmap.js). Minor.
- **Canvas resize on every paint**: `paintSpecks` sets `speckCanvas.width/height` and `style.width/height` and re-`scale()`s the context on every call, even when the map size has not changed — [`devmap.js:734-745`](site/devmap.js). Assigning `canvas.width` clears and reallocates the backing store; at `devicePixelRatio` 2–3 on a phone that is a multi-megabyte allocation per paint. It also calls `map.latLngToContainerPoint` once per speck inside the draw loop — [`devmap.js:747`](site/devmap.js) — which is projection math, not layout, so not thrash, but it is per-speck work on the main thread. Guarding the resize on changed dimensions is a cheap, safe fix.
- `paintSpecks()` is called from `decorate()` on hover transitions — [`devmap.js:841-844`](site/devmap.js) — so a mouse moving across the map can trigger a full canvas reallocation and repaint per hover change. Combined with the `map.on('mousemove')` handler at [`devmap.js:785-789`](site/devmap.js) which writes `node.style.cursor` every move, this is the hottest interactive path in the file.
- `fitWorkspace()` reads `getComputedStyle(tabs).position`, two `getBoundingClientRect()` and `scrollY`, then writes `wrap.style.height` — [`devmap.js:495-506`](site/devmap.js) — and it is called from inside the `ResizeObserver` callback at [`devmap.js:983`](site/devmap.js), which then calls `map.invalidateSize()` at [`devmap.js:984`](site/devmap.js). Writing a height from inside a ResizeObserver on the observed element's ancestor is a resize-loop shape; the `if (wrap.style.height !== ...)` guard at [`devmap.js:505`](site/devmap.js) is what prevents it from oscillating. That guard is load-bearing and untested.
- `padding()` reads `node.clientWidth`/`clientHeight` and `wrap.classList.contains` on every `fit()` — [`devmap.js:849-859`](site/devmap.js); `wide()` reads `node.clientWidth` again — [`devmap.js:847`](site/devmap.js). Several independent layout reads per filter change.
- `drawChart()` rebuilds **every bar element from scratch** on every `apply()` — `node.replaceChildren(head, bars, axis)` with a fresh loop over 24 months — [`devmap.js:606-628`](site/devmap.js), called at [`devmap.js:396`](site/devmap.js). Bounded at 24 bars so cheap, but it destroys and recreates focus-bearing buttons; see the test-gap section.

### Inferences
- The two changes I would make first, both verifiable by reading alone: guard the canvas resize in `paintSpecks` on changed size, and replace the `querySelectorAll` sweeps in `select`/`close` with remembered node references. Both are small and remove per-interaction O(N) DOM traversal.
- Whether any of this is *perceptible* on the target device is unknown without a profile. The repo's own harness has the hooks to find out (`node.dataset.drawMs` at [`devmap.js:961`](site/devmap.js)), but nothing asserts on it — see below.

## What the 702-line devmap-check asserts, and what it does not

### Takeaway
It is a genuinely strong **correctness** check: every filter is verified against an independently reimplemented expectation, on desktop and phone, including counts, visible rows, off-map rows, and the pins Leaflet actually drew. Its blind spots are almost entirely **data loading, lifecycle and performance regressions** — exactly the things that fail quietly.

### What it does assert
- Independent expectation, deliberately not importing the production filter: "Independent expectation (deliberately not importing site/market.js)" with its own `expected()` reimplementation of query/place/work/public/cost/status/filed/since — [`devmap-check.mjs:81-106`](backend/test/browser/devmap-check.mjs). This is the test's strongest design decision: a bug in `filterProjects` cannot hide.
- Data audit on the built file: every project has city/name/id, every cost positive, work ∈ {New construction, Addition}, ISO filing dates, lat/lng in pairs — [`devmap-check.mjs:69-73`](backend/test/browser/devmap-check.mjs). Duplicate ids within a metro are **printed, not failed** — "Not a failure: the map keys pins by project, not id. Reported because Follow uses the id." — [`devmap-check.mjs:74-79`](backend/test/browser/devmap-check.mjs).
- Every filter alone (`for (const [value] of options) await check(...)` — [`devmap-check.mjs:231`](backend/test/browser/devmap-check.mjs)) and five named combinations — [`devmap-check.mjs:238-242`](backend/test/browser/devmap-check.mjs) — each asserting count, list length, drawn markers, the pins text and the empty state together at [`devmap-check.mjs:216`](backend/test/browser/devmap-check.mjs).
- Menu options exactly match the values in the data, with counts — [`devmap-check.mjs:221-229`](backend/test/browser/devmap-check.mjs).
- Legend: counts sum to the shown total; hiding a category removes exactly its rows and its pins; a hidden category keeps its count; re-showing restores — [`devmap-check.mjs:248-272`](backend/test/browser/devmap-check.mjs).
- Chart: bar counts match filings per month; a bar click filters from that month on and a second click clears — [`devmap-check.mjs:273-291`](backend/test/browser/devmap-check.mjs).
- Sort: all three orders verified on the filtered list, with the duplicate-id caveat handled — [`devmap-check.mjs:292-309`](backend/test/browser/devmap-check.mjs).
- Panel: pin click opens it and highlights the row, two links present, panel sits inside the map, close works, next/prev step in list order, Escape closes and returns focus to the row — [`devmap-check.mjs:396-429`](backend/test/browser/devmap-check.mjs).
- `Clear all` resets search, menus, legend, chart month and the hiring toggle together — [`devmap-check.mjs:431-446`](backend/test/browser/devmap-check.mjs).
- Keyboard (desktop only): full Tab order through the side column and the pill row, and a visible focus ring on every control — [`devmap-check.mjs:448-493`](backend/test/browser/devmap-check.mjs).
- Layout/workspace: map starts under the header and on screen, ends above the fixed tabs, legend labels unclipped, no sideways scroll on phone — [`devmap-check.mjs:159-190`](backend/test/browser/devmap-check.mjs).
- Phone-specific: the "Search & project list" button scrolls and focuses, typing filters, the pill row scrolls sideways and the page does not — [`devmap-check.mjs:528-559`](backend/test/browser/devmap-check.mjs).
- Named-regression anchors: the Merc (TABS2025017471/77) has no city duplicate and a pin with stated provenance — [`devmap-check.mjs:561-580`](backend/test/browser/devmap-check.mjs); PDL Club (TABS2026006871) is findable and its small pin shows — [`devmap-check.mjs:594-617`](backend/test/browser/devmap-check.mjs); smaller-filing pins drawn, "Show on map" opens the popup, a filter hides them — [`devmap-check.mjs:624-646`](backend/test/browser/devmap-check.mjs).
- Two soft performance assertions that **do** fail: search updates within 400 ms — [`devmap-check.mjs:331`](backend/test/browser/devmap-check.mjs) — and "filter change paints within 150 ms" — [`devmap-check.mjs:347`](backend/test/browser/devmap-check.mjs). Both run on the **unthrottled** desktop/phone contexts, not the throttled one.
- Zero page errors on each viewport — [`devmap-check.mjs:668`](backend/test/browser/devmap-check.mjs). This is the catch-all that makes many untested paths at least not throw.

### Untested flows, ranked by how quietly they would fail
1. **The slow-phone budget does not exist.** The whole block at [`devmap-check.mjs:671-696`](backend/test/browser/devmap-check.mjs) prints a markdown table (`console.log('| ${city} | ... |')` at line 694) and never calls `log()`. There is no threshold and nothing contributes to the `failed` count at [`devmap-check.mjs:700-701`](backend/test/browser/devmap-check.mjs). A change that doubles time-to-map on a throttled phone, or doubles the downloaded bytes, passes CI with a green tick and a worse number in a log nobody reads. This is the single quietest possible failure in the feature. Commit `49608bc` ("Time the development map on a slow phone in the site build check") added measurement only — the diff is 36 added lines in the check file and nothing else.
2. **The stage-2 fetch failing is not tested.** `loadDevFile`'s `.catch(() => devFiles.set(city, 'failed'))` — [`markets-view.js:863`](site/markets-view.js) — swallows the error silently with no user-visible state. The map then shows only the headline projects (300–400 of possibly thousands) and looks completely normal: correct counts, correct pins, correct coverage note, just a fraction of the data. The check instead *waits for* the full file (`waitFull` at [`devmap-check.mjs:35-42`](backend/test/browser/devmap-check.mjs)) and fails only on timeout; it never serves a 500 for `developments/*.json` and asserts what the user sees. A broken path, a Supabase RLS change, or a renamed slug would produce a silently truncated map.
3. **Nothing asserts `dataset.drawMs`.** The map already instruments its own draw cost at [`devmap.js:869, 961`](site/devmap.js) and the check never reads it. A regression in the pill packing or the fan-out would show up nowhere.
4. **`disposeMap()` and the city switch are barely covered.** The city switch is asserted only by title text and hash — [`devmap-check.mjs:660-667`](backend/test/browser/devmap-check.mjs). The intricate Leaflet teardown workaround — `liveMap.stop(); liveMap._animatingZoom = false; liveMap.remove();` with its comment about Leaflet 1.9's "untracked 250 ms timer" — [`devmap.js:85-95`](site/devmap.js) — depends on a private field and would break on a Leaflet upgrade. It would surface only as an async `pageerror` after the listener window; the test deliberately switches metros in a fresh tab to avoid "tearing down a map that is still mid-animation" — [`devmap-check.mjs:496`](backend/test/browser/devmap-check.mjs) — i.e. the check actively avoids the case most likely to break. Likewise the `map !== liveMap` guards at [`devmap.js:868, 994, 1003, 1013, 1023, 1031`](site/devmap.js) are never exercised.
5. **The `fitWorkspace` resize-loop guard.** [`devmap.js:495-506`](site/devmap.js) writes a height from a `ResizeObserver`; only the `if (wrap.style.height !== ...)` guard stops it oscillating. Nothing tests orientation change, keyboard-open viewport shrink, or a tab switch. A regression here is a janky or infinitely-resizing phone map that still passes every count assertion.
6. **`FIRST_ROWS` tail fill and its generation guard.** Nothing asserts that rows 301..N arrive, nor that rapidly changing filters cannot interleave two tails. `waitFull` waits for the full count so it *incidentally* covers arrival, but a regression that drops the tail entirely when `turn` bookkeeping breaks would show as a short list that `waitFull` reports as a timeout with a confusing message, not as a named failure.
7. **The `last` key short-circuit in `api.show()`.** [`devmap.js:1014-1016`](site/devmap.js) skips the refit when the key is unchanged. If the key were ever computed wrongly (e.g. after the project array identity changes on a stage-2 swap), the map would silently stop refitting on filter changes while the list kept updating. Not tested.
8. **The hiring toggle's correctness.** `.devx-toggle` is clicked only as part of the Clear-all setup — [`devmap-check.mjs:435`](backend/test/browser/devmap-check.mjs) — and its *filtering* result is never compared to an expectation, because `expected()` has no hiring branch. `hiringOnly` is module-level state at [`devmap.js:108`](site/devmap.js), as are `sort` [`devmap.js:106`](site/devmap.js) and `filters` [`devmap.js:61`](site/devmap.js), so they leak across cities and across card rebuilds by design — the `filtersCity !== city` reset at [`devmap.js:165-168`](site/devmap.js) resets only `place`. A regression where a stale `hiringOnly` or `sort` survives a city switch is untested.
9. **The approximate/dashed-pin and leader-line rendering.** `approximate` affects the speck stroke [`devmap.js:753-758`](site/devmap.js), the pill class [`devmap.js:704`](site/devmap.js) and the `.devx-leader` polylines [`devmap.js:953`](site/devmap.js). None is asserted; only the coverage-note *text* counts are — [`devmap-check.mjs:586-591`](backend/test/browser/devmap-check.mjs).
10. **Reports are tested only as absent.** `log('no report form while reporting is off', (await page.locator('.dev-report').count()) === 0)` — [`devmap-check.mjs:648`](backend/test/browser/devmap-check.mjs). The pin-drop flow at [`devmap.js:820-826`](site/devmap.js) and `reports.picking()`'s interaction with the speck-zoom click handler at [`devmap.js:780-784`](site/devmap.js) — two separate `map.on('click')` handlers whose order matters — are entirely untested. When reporting is switched on, a click could both drop a pin and zoom the map, and nothing would catch it.
11. **Double render on first open.** Nothing asserts that `developmentMap()` is constructed once rather than twice, or that the first (headline-only) paint is not visibly wrong. A regression to three or four renders is invisible.
12. **Coverage of the `cache: 'no-cache'` behaviour / repeat-visit cost.** The check always loads cold.

### Inferences
- Minimal, high-value additions, in order: (a) turn the slow-phone table into `log()` assertions with explicit budgets — map-ready seconds, full-list seconds, total downloaded MB, and each file's gzip MB; (b) a route that 500s `developments/*.json` and asserts the map still renders the headline set *and* says something to the user; (c) assert `Number(mapNode.dataset.drawMs)` under a budget after a filter change and after a pan; (d) a city switch in the *same* tab with `pageerror` collection held open for ~1 s afterwards, to cover `disposeMap`.
- Budget numbers have to come from a real CI run's printed table, since the build outputs are absent here. Setting them generously (e.g. 1.5–2x the current observed value) still catches doublings, which is what matters.

## Is the slow-phone check a real budget?

### Takeaway
**No.** It is measurement only. There is no threshold and no failure path.

### Cited findings
- The emulation is realistic: `Network.emulateNetworkConditions` with 150 ms latency and 1.6 Mbps (×0.9) down, plus `Emulation.setCPUThrottlingRate { rate: 4 }`, described as "A mid-range phone on a slow connection: Lighthouse's 'Slow 4G' (150 ms, 1.6 Mbps down) and a 4x slower CPU" — [`devmap-check.mjs:671-683`](backend/test/browser/devmap-check.mjs).
- Bytes are counted off CDP: `cdp.on('Network.loadingFinished', (e) => (bytes += e.encodedDataLength))` — [`devmap-check.mjs:684-685`](backend/test/browser/devmap-check.mjs).
- Three timings are taken: time to `dataset.pins != null` ("Map ready") and time to the full list count ("Full list"), with 180 s timeouts — [`devmap-check.mjs:686-692`](backend/test/browser/devmap-check.mjs). The full-list wait is `.catch(() => null)` — a timeout there is swallowed and the table simply prints the 180 s figure.
- The output is a single `console.log` of a markdown row — [`devmap-check.mjs:694`](backend/test/browser/devmap-check.mjs). **No `log()` call anywhere between lines 671 and 696**, so `results` is untouched and `failed` at [`devmap-check.mjs:700`](backend/test/browser/devmap-check.mjs) cannot be affected.
- It runs for at most two metros, hardcoded: `for (const city of ['San Antonio', 'Houston'].filter((c) => byCity.has(c)))` — [`devmap-check.mjs:676`](backend/test/browser/devmap-check.mjs). A regression confined to Dallas or Austin is not measured at all.
- The gzip-encoding path in the local server exists specifically for this: "Compressed as GitHub Pages serves it, for the slow-phone timing" — [`devmap-check.mjs:117-121`](backend/test/browser/devmap-check.mjs). Good fidelity, wasted on an unasserted number.
- The two thresholds that **do** exist (400 ms search, 150 ms filter paint — [`devmap-check.mjs:331, 347`](backend/test/browser/devmap-check.mjs)) run on the **un-throttled** contexts. The 400 ms one is also weak by construction: the debounce is 120 ms, so it allows 280 ms of actual work; and it waits on a `MutationObserver` on `.dev-count` with a 3 s fallback `setTimeout(r, 3000)` at [`devmap-check.mjs:327`](backend/test/browser/devmap-check.mjs) — if the count never changes, `typed` reads ~3000 and the assertion fails, which is at least the right direction.

### Inferences
- The fix is two or three lines per measured quantity and needs no new infrastructure: the numbers are already computed. The hardest part is choosing budgets, which requires one CI run to read current values.
- Because the full-list wait swallows its timeout, a change that makes the full list never arrive on a throttled phone shows up as "180.0 s" in a table and a passing check. That is worth calling out specifically.

## Pure functions that could be unit tested cheaply and are not

### Takeaway
`devmap.js` holds a handful of genuinely pure, exported-or-easily-exportable functions with real edge cases, and the only ones currently unit tested are the ones that happen to live in `devreports.js` and `market.js`. The map's own formatting and geometry helpers have **zero** unit coverage and are exercised only through a 702-line browser check.

### Cited findings
- **Already covered elsewhere** (so the pattern exists and is cheap): `backend/test/devreports-site.test.ts` imports `coverageNote, matchSmaller, reportError, reportRow, reportStatus` straight from `site/devreports.js` — [`backend/test/devreports-site.test.ts:1-2`](backend/test/devreports-site.test.ts) — with describes for the report form, the coverage note, smaller-filings search and pages read. `backend/test/developments.test.ts` covers `cityProjects` [lines 324-326], `markerRadius` [330-332], `filterProjects` via an `ids()` helper [360], `activeFilterCount` [386] and `filterChoices` [390].
- **Untested and pure, in `devmap.js`:**
  - `money(cost)` — [`devmap.js:1328-1334`](site/devmap.js). Four branches with boundary behaviour at 1e6/1e8/1e9, a falsy-cost early return (`if (!(cost > 0)) return ''` — note it returns an empty string, which callers then paper over with `money(cost) || '$0'` at [`devmap.js:362`](site/devmap.js) and `'Not listed'` at [`devmap.js:1186`](site/devmap.js)). Not exported. Easily the highest value-per-line test in the file: it drives the pill width, the summary total and the panel tile.
  - `pillWidth(text)` — [`devmap.js:639`](site/devmap.js), `34 + text.length * 7.4 + 12`. A magic formula that directly determines pill overlap; a font or padding change silently desynchronises it from the rendered pill and pills start overlapping. Trivially testable as a monotonic function, and worth a browser-side assertion that the computed width matches the real `offsetWidth`.
  - `dueDate(due)` — [`devmap.js:1318-1326`](site/devmap.js). **Already exported** and untested. Regex parse, UTC handling, the `h === '00' && mi === '00'` date-only case, 12-hour conversion via `+h % 12 || 12`, and an unparsable input falling through to `due ?? ''`. Pure, no DOM.
  - `sqft(n)` — [`devmap.js:1265-1269`](site/devmap.js). Three branches at 1e4/1e6.
  - `MONTH_FMT(iso)` — [`devmap.js:1141-1144`](site/devmap.js) and `monthLabel(key, long)` — [`devmap.js:600-603`](site/devmap.js). Both regex/split-based, both silently return `''` or `undefined ...` on malformed input (`monthLabel` does no validation: `MONTHS[+m - 1]` on a bad key yields `undefined`).
  - `locationNote(project)` — [`devmap.js:1061-1067`](site/devmap.js). Pure, five-way precedence (awaiting → no coords → approximate → locatedFrom → source). The ordering is user-facing provenance text and the browser check only regex-matches it loosely: `/not on the map|no map location|pending|await/i` at [`devmap-check.mjs:516`](backend/test/browser/devmap-check.mjs). A precedence bug (approximate taking priority over awaiting, say) would pass.
  - `pinLabel(project, cat)` — [`devmap.js:652-654`](site/devmap.js). Pure join with filter; it is the pin's whole accessible name.
  - `smallerOf(data, city)` — [`devmap.js:1110-1112`](site/devmap.js). Pure filter.
  - The `free(box)` overlap predicate — [`devmap.js:927`](site/devmap.js) — and the fan-out offset maths — [`devmap.js:887-911`](site/devmap.js) — are pure geometry trapped inside `draw()`. Lifting `free` and a `fanOffsets(n)` helper to module scope would make the ring/spiral invariant ("no two icons within PIN px of each other, for n = 1..50") a three-line unit test. **This is the highest-value extraction**: it is the only place in the file where a silent visual regression (overlapping icons) has no assertion of any kind.
- **Untested and pure, in `devicons.js`:** `glyphSvg(key)` and `categoryClass(key)` — [`site/devicons.js:28-35`](site/devicons.js). `categoryClass` has real logic (unknown key → `other`, `DARK_GLYPH` membership → extra class) and no test. `categoryBadge` needs a DOM but the repo already runs DOM-less string functions in vitest.
- `site/devmap.js` currently exports `TILES, ATTRIBUTION, CENTERS, loadLeaflet, disposeMap, developmentMap, toggleDetail, bidsSection, dueDate` — of these only `dueDate` and `CENTERS` are testable without a DOM, and neither is tested.

### Inferences
- A single new `backend/test/devmap-site.test.ts`, mirroring the existing `devreports-site.test.ts` import pattern, could cover `money`, `sqft`, `dueDate`, `MONTH_FMT`, `monthLabel`, `locationNote`, `pinLabel`, `smallerOf`, `pillWidth`, `glyphSvg` and `categoryClass` in well under 100 lines, requiring only that six of them be exported. That converts a large fraction of the file's silent-failure surface from "covered by a 702-line browser run" to "covered in milliseconds".
- The `money()` empty-string return is the kind of thing a unit test pins down and nothing else does: two call sites compensate for it differently ([`devmap.js:362`](site/devmap.js) vs [`devmap.js:1186`](site/devmap.js)) and a third, `pillWidth(money(p.cost))` at [`devmap.js:936`](site/devmap.js), computes a 46 px pill for a zero-cost project.

### Gaps
- I did not run the test suite or the browser check, so I cannot confirm the current pass/fail state or any actual timing figure. Every performance claim above is from reading code; none is profiled. The distinction matters most for the canvas-resize and the `select()` layout-thrash findings, which are structurally clear but whose magnitude is unknown.
