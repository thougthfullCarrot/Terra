# Accessibility and responsive behaviour of the development map

Scope: `site/devmap.js` (1341 lines), `site/devicons.js`, `site/style.css` (180 KB; the map's rules run roughly 7690–8800 plus phone overrides at 8790–8910 and 9030–9110), `site/market.js` (category colours), `site/devreports-view.js`, and the existing browser check `backend/test/browser/devmap-check.mjs`.

All line numbers are from the files as they stand at commit `a0b7c60`. "Confirmed" below means readable directly from the source; "needs a browser" means the code makes it likely but a running page is required to settle it (computed colour ratios, measured pixel sizes, cascade order, clipping).

## Keyboard: can every interactive element be reached and operated without a mouse?

### Takeaway
The whole left-hand side (search, legend, sort, list) and the whole filter row are real `button`/`select`/`details` elements, reachable in a sensible order, and `devmap-check.mjs` already asserts that order and the focus rings. The failures are all on the map surface: the canvas "specks" and the circle-marker pins (smaller filings, verified community reports) are pointer-only, and the pins that *are* focusable are an unbounded, unskippable run of tab stops that gets torn down under the user on every pan, zoom or filter change.

### Cited findings
- The left column's controls are native and operable: legend categories are `button` with `type=button` and `aria-pressed` — "`const button = el('button', 'devx-legend-item'); button.type = 'button';`" — [site/devmap.js:222-235](site/devmap.js); sort is a `role=group` of three buttons with `aria-pressed` — [site/devmap.js:241-254](site/devmap.js), [site/devmap.js:370](site/devmap.js); each list row is a `button.dev-pick` — [site/devmap.js:1076-1103](site/devmap.js). — [site/devmap.js](site/devmap.js)
- Filters are `select` elements inside `label.devx-pill`, each with an explicit `aria-label`, and the overflow group is a native `details`/`summary` — [site/devmap.js:525-554](site/devmap.js). `Escape` closes the open `details` and returns focus to the summary: "`if (event.key === 'Escape' && more.open) { more.open = false; moreSummary.focus(); }`" — [site/devmap.js:555-560](site/devmap.js). — [site/devmap.js](site/devmap.js)
- Chart months are buttons with `aria-pressed` and a full `aria-label` ("`${monthLabel(month, true)}: ${count} filings. Show filings from this month on`") — [site/devmap.js:612-623](site/devmap.js). — [site/devmap.js](site/devmap.js)
- Map pins are focusable and named. `L.marker(..., { icon, keyboard: true, riseOnHover: true })` — [site/devmap.js:710](site/devmap.js) — and on `add` the icon gets the name plus an Enter/Space handler: "`icon.setAttribute('aria-label', label); icon.onkeydown = pressed(() => onPick(project));`" — [site/devmap.js:715-722](site/devmap.js), with `pressed()` handling Enter and Space and calling `preventDefault` — [site/devmap.js:641-649](site/devmap.js). Leaflet 1.9.4 is the pinned version (`"leaflet": "1.9.4"` — [backend/package.json:40](backend/package.json)); its `Marker._initIcon` sets `tabIndex = '0'` and `role="button"` when `keyboard` is true, so pins are genuine buttons. — [site/devmap.js](site/devmap.js)
- **Specks are pointer-only.** Below `SPREAD_ZOOM = 16` a project only gets a price pill if its box does not overlap one already placed; everything else becomes a speck — "`nextSpecks.push({ p, color: ... })`" — [site/devmap.js:926-946](site/devmap.js). Specks are painted on a single `<canvas>` (`L.DomUtil.create('canvas', 'devx-specks')`, appended to the overlay pane) — [site/devmap.js:730-770](site/devmap.js) — with no DOM node, no tab stop, no name and no role. They are reachable only by `map.on('click')` hit-testing within 8 px (`bestD = 64`) and by `mousemove` — [site/devmap.js:771-789](site/devmap.js). At a metro's default fit zoom this is the *majority* of projects. — [site/devmap.js](site/devmap.js)
- **Smaller-filing pins and verified community report pins are pointer-only.** Both are `L.circleMarker` with `bindPopup`/`bindTooltip` and no keyboard handling — [site/devmap.js:797-818](site/devmap.js). Leaflet's SVG renderer does not give `Path` layers a `tabindex` or a role (only `Marker` honours `options.keyboard`), so these popups cannot be opened from the keyboard. Smaller filings have a text alternative — the Smaller filings list below the map wires `reports.setOpenSmall((id) => drawn.openSmall(id))` — [site/devmap.js:481](site/devmap.js), [site/devmap.js:1001-1009](site/devmap.js). The *verified community report* pins at [site/devmap.js:813-819](site/devmap.js) are added straight to the map with no list equivalent created in `devmap.js`. — [site/devmap.js](site/devmap.js)
- **No way to skip the pins.** Every marker in view is in `layer` and therefore a tab stop; the draw loop reports the count as `node.dataset.drawn` — [site/devmap.js:958](site/devmap.js) — and `drawn` is bounded only by how many pills/icons fit the viewport. There is no "skip map" link, no `tabindex=-1` on off-interest pins, and no grouping. — [site/devmap.js](site/devmap.js)
- **Pins are destroyed under the keyboard user.** Each redraw removes markers not in the new `want` set: "`for (const marker of [...layer.getLayers()]) if (!want.has(marker)) layer.removeLayer(marker);`" — [site/devmap.js:948-950](site/devmap.js) — and `redraw` is bound to `zoomend moveend` ([site/devmap.js:968](site/devmap.js)) while `apply()` calls `map?.show(ids)` → `fit()` → `draw()` on every filter and every debounced keystroke ([site/devmap.js:409](site/devmap.js), [site/devmap.js:972-978](site/devmap.js)). The in-code comment claims "kept pins stay on the page, so focus and hover survive a pan" — true only for pins that survive the filter. — [site/devmap.js](site/devmap.js)
- Dropping a community-report pin is a map click: `state.picking` with the instruction "Click the spot on the map." — [site/devreports-view.js:129-131](site/devreports-view.js) — and the map side only listens for `map.on('click')` — [site/devmap.js:821-826](site/devmap.js). The same component offers an address field as the alternative ("Or give an address above."), so there is a non-pointer path. — [site/devreports-view.js](site/devreports-view.js)
- `Escape` anywhere inside the card closes an open panel and is explicitly scoped so it does not steal the `details` key: "`if (event.key === 'Escape' && selected && !event.target.closest?.('.devx-more'))`" — [site/devmap.js:464-471](site/devmap.js). — [site/devmap.js](site/devmap.js)
- Already asserted by the check, so these are protected regressions rather than open questions: tab order "search → N legend categories → 3 sorts → first project" and "every filter menu, More, Firms hiring now and Clear all in order" — [backend/test/browser/devmap-check.mjs:467-476](backend/test/browser/devmap-check.mjs); Enter on More, a legend item, a chart bar and Clear all — [backend/test/browser/devmap-check.mjs:479-492](backend/test/browser/devmap-check.mjs). — [backend/test/browser/devmap-check.mjs](backend/test/browser/devmap-check.mjs)
- **The keyboard walk is skipped on phones**: the whole block is wrapped in `if (!vp.mobile) {` — [backend/test/browser/devmap-check.mjs:449](backend/test/browser/devmap-check.mjs). No keyboard assertion exists at 390 px. — [backend/test/browser/devmap-check.mjs](backend/test/browser/devmap-check.mjs)

### Inferences
- No keyboard *trap* exists: every bespoke key handler (`pressed`, the two `Escape` handlers) is additive, the panel is not a `dialog`, and nothing holds focus. The problem is the opposite — focus leaks to `body` when a focused marker is removed.
- WCAG 2.1.1 Keyboard (A) is met for the content only because the project list is a complete parallel control surface; the *map* itself fails it for specks, smaller filings and report pins. WCAG 2.4.1 Bypass Blocks (A) is the cleaner citation for the unskippable pin run.

### Gaps
- The exact `dataset.drawn` value at a metro's default zoom (how many tab stops the map actually inserts) needs a running browser; the check records the number but never bounds it.
- Whether the verified community report pins have a text list elsewhere in `devreports-view.js` was not fully traced — only the `picking` flow was read.

### Concrete fixes
1. Give the map a bypass: a visually-hidden "Skip the map pins" link before `mapNode`, or put the pin layer behind a single `role="application"` entry point with arrow-key navigation, so Tab passes over the pins in one step.
2. Make specks reachable without the mouse: expose the speck set as a visually-hidden list of buttons inside the map region (name from `pinLabel`, action = the existing `map.setView(..., SPREAD_ZOOM)` zoom-in at [site/devmap.js:783](site/devmap.js)), or state in the map's label that specks are listed in the project list and rely on that.
3. Add `keyboard` behaviour to the two `circleMarker` families: after `addTo`, set `tabindex="0"`, `role="button"` and an `aria-label` on `marker.getElement()`, and bind Enter/Space to `openPopup()` with the existing `pressed()` helper.
4. Before removing a marker in the redraw at [site/devmap.js:949](site/devmap.js), check `marker.getElement()?.contains(document.activeElement)` and, if so, move focus to the map region (`mapNode.tabIndex = -1; mapNode.focus()`) rather than letting it fall to `body`.
5. Drop the `if (!vp.mobile)` guard at [backend/test/browser/devmap-check.mjs:449](backend/test/browser/devmap-check.mjs) so the tab-order and focus-ring assertions also run at 390 px.

## Focus management: does focus move into the panel, return on close, and stay visible?

### Takeaway
Closing is handled well and is already covered by a test; **opening is not handled at all**. The detail panel is given `tabIndex = -1` and a `focus()` path, but no caller ever asks for it, so a large panel appears with focus left behind on the row or the pin — and the panel's focus ring is suppressed by `outline: none`, so even if focus did land there nothing would show.

### Cited findings
- The panel is built to be focusable and `select()` accepts a `focus` flag: "`panel.tabIndex = -1;`" — [site/devmap.js:292-295](site/devmap.js) — and "`if (focus) panel.focus({ preventScroll: true });`" — [site/devmap.js:439](site/devmap.js). — [site/devmap.js](site/devmap.js)
- **No caller passes `focus: true`.** The two entry points are the list row — "`(project) => select(project, { fly: true, reveal: true })`" — [site/devmap.js:319](site/devmap.js) — and the map pin — "`(project) => select(project, { fly: true, focus: false })`" — [site/devmap.js:477](site/devmap.js), where `focus: false` is passed *explicitly*. `focus` defaults to `false` in the signature — [site/devmap.js:420](site/devmap.js). — [site/devmap.js](site/devmap.js)
- The panel's focus indicator is removed: "`.devx-panel { ... outline: none; }`" — [site/style.css:8531-8547](site/style.css). — [site/style.css](site/style.css)
- Closing is correct. `close()` returns focus to the originating row when focus was inside the panel — "`if (was && panel.contains(document.activeElement)) items.get(was)?.querySelector('.dev-pick')?.focus({ preventScroll: true });`" — [site/devmap.js:452-461](site/devmap.js) — and the `Escape` handler returns focus unconditionally — [site/devmap.js:464-471](site/devmap.js). — [site/devmap.js](site/devmap.js)
- `step()` keeps focus coherent while walking the panel: after re-rendering it refocuses the matching nav button — "`const nav = panel.querySelector(by < 0 ? '.devx-prev' : '.devx-next'); if (by && nav && !nav.disabled) nav.focus(...)`" — [site/devmap.js:443-450](site/devmap.js). — [site/devmap.js](site/devmap.js)
- A filter change that removes the selected project calls `close()` — "`if (selected && !ids.has(selected)) close();`" — [site/devmap.js:410](site/devmap.js). Because `close()`'s focus return is conditional on focus being inside the panel, focus sitting on a now-removed *pin* is not recovered. — [site/devmap.js](site/devmap.js)
- Focus visibility elsewhere is actively tested: "`const ring = (cs.outlineStyle !== 'none' && parseFloat(cs.outlineWidth) > 0) || cs.boxShadow !== 'none';`" and "`every control shows a visible keyboard focus ring`" — [backend/test/browser/devmap-check.mjs:455-478](backend/test/browser/devmap-check.mjs). The panel container is not among the walked controls. — [backend/test/browser/devmap-check.mjs](backend/test/browser/devmap-check.mjs)
- Escape-and-return is already asserted: "`${v}: Escape closes the panel and returns focus to its row`" — [backend/test/browser/devmap-check.mjs:427-429](backend/test/browser/devmap-check.mjs). — [backend/test/browser/devmap-check.mjs](backend/test/browser/devmap-check.mjs)
- On phones the panel is a sheet covering from `top: 22%` to `bottom: 6px` and **hides the filter row and the chart while it is open**: "`.devx-mapwrap.narrow.panel-open .devx-filters, .devx-mapwrap.narrow.panel-open .devx-chart { display: none; }`" — [site/style.css:8561-8563](site/style.css), sheet geometry at [site/style.css:9080-9086](site/style.css). Any element inside those two blocks that holds focus when a project is opened is `display: none`'d, which drops focus to `body`. — [site/style.css](site/style.css)

### Inferences
- Confirmed failure of WCAG 2.4.3 Focus Order (A) for the phone sheet in particular: a sheet covering roughly 78% of the map opens with focus still on the row behind it, so the next Tab continues through the list underneath rather than into the sheet, and `Escape` is the only documented way out.
- WCAG 2.4.7 Focus Visible (AA): `outline: none` on `.devx-panel` is a confirmed suppression; its practical impact is currently masked by the fact that focus never goes there.
- `step()` focusing a nav button is the reason `projectPanel` is re-rendered wholesale without an announcement problem for keyboard users — but it only helps *after* the first open.

### Gaps
- Whether the phone sheet needs to behave as a modal (focus trap + `aria-modal`) or as a non-modal region is a design decision; the code currently commits to neither.

### Concrete fixes
1. Pass `focus: true` from both entry points ([site/devmap.js:319](site/devmap.js) and [site/devmap.js:477](site/devmap.js)), at minimum when `mapWrap.classList.contains('narrow')`, so the phone sheet takes focus.
2. Replace `outline: none` at [site/style.css:8547](site/style.css) with a `:focus-visible` ring on `.devx-panel` (the codebase's own convention — see the ring test at [backend/test/browser/devmap-check.mjs:458](backend/test/browser/devmap-check.mjs)).
3. Give the panel a heading relationship: the title already exists (`h3.devx-panel-title` at [site/devmap.js:1177](site/devmap.js)); give it an id and swap the static `aria-label="Project details"` ([site/devmap.js:293](site/devmap.js)) for `aria-labelledby` so the focused panel announces the project name.
4. On the phone, treat the sheet as modal: `role="dialog" aria-modal="true"`, trap Tab inside it while `.narrow.panel-open`, since the filters and chart behind it are `display: none` anyway.
5. In `close()` ([site/devmap.js:460](site/devmap.js)), broaden the focus-return test from `panel.contains(document.activeElement)` to "focus is in the panel *or* on the chosen project's pin".
6. Add an assertion to the check: after a row click and after a pin click, `document.activeElement` is inside `.devx-panel` (desktop and phone).

## Semantics: do pins, clusters and legend items have names and roles? Is the map labelled, and is the list a real alternative?

### Takeaway
Semantics are unusually good for a hand-built map: the map and the list are both labelled regions, pins carry real `role=button` + `aria-label`, and category meaning is carried by a distinct glyph per category, not by colour. The project list *is* a genuine non-visual alternative for the project data. Two things are not covered: the cost-by-category bar is `aria-hidden` with no text equivalent, and clusters no longer exist in this version despite what the test comments say.

### Cited findings
- The card, the list side and the map are all labelled regions: `box.setAttribute('aria-labelledby', 'dev-title')` with `title.id = 'dev-title'` — [site/devmap.js:119](site/devmap.js), [site/devmap.js:128-129](site/devmap.js); "`side.setAttribute('aria-label', 'Projects'); side.setAttribute('role', 'region');`" — [site/devmap.js:181-184](site/devmap.js); "`mapNode.setAttribute('role', 'region'); mapNode.setAttribute('aria-label', 'Map of ${city} metro development projects');`" — [site/devmap.js:285-287](site/devmap.js). The list is an `ol` with "`list.setAttribute('aria-label', '${city} metro development projects')`" — [site/devmap.js:267-268](site/devmap.js). — [site/devmap.js](site/devmap.js)
- Pin names are composed, not bare coordinates: "`return [project.name, cat?.label, money(project.cost), project.approximate ? 'approximate location' : ''].filter(Boolean).join(', ');`" — [site/devmap.js:651-654](site/devmap.js) — and applied as both `aria-label` and tooltip — [site/devmap.js:711](site/devmap.js), [site/devmap.js:717](site/devmap.js). — [site/devmap.js](site/devmap.js)
- Category is carried by shape as well as colour. `devicons.js` ships a distinct 24×24 glyph per category (house, office tower, saw-tooth factory, medical cross, civic pediment, storefront, outline) — [site/devicons.js:7-22](site/devicons.js) — and documents the intent: "drawn white or dark on the category's color, so a category reads from its shape as well as its color" — [site/devicons.js:1-4](site/devicons.js). Light colours get a dark glyph: "`const DARK_GLYPH = new Set(['industrial', 'other']);`" — [site/devicons.js:25](site/devicons.js). — [site/devicons.js](site/devicons.js)
- The badge is correctly named or correctly hidden depending on context: "`if (label && cat?.label) { badge.setAttribute('role', 'img'); badge.setAttribute('aria-label', cat.label); ... } else badge.setAttribute('aria-hidden', 'true');`" — [site/devicons.js:41-51](site/devicons.js). The list passes `label` on (default `true`) — [site/devmap.js:1079](site/devmap.js) — while the legend and panel pass `{ label: false }` because a text label sits beside it — [site/devmap.js:226](site/devmap.js), [site/devmap.js:1151](site/devmap.js). Glyph SVGs are `aria-hidden="true" focusable="false"` — [site/devicons.js:29](site/devicons.js). — [site/devicons.js](site/devicons.js)
- The list is a full text equivalent of each project: category badge (named), name, `place · facility · work`, status/"Details pending from the state"/"Not on the map"/"Approximate pin"/"Site point" tags, a hiring tag, and cost — [site/devmap.js:1072-1104](site/devmap.js). Pin provenance is also written out in prose in the panel: `locationNote()` returns e.g. "Approximate: the pin is near the ZIP code center, not the exact site." — [site/devmap.js:1060-1067](site/devmap.js) — and the coverage note states the located/approximate/awaiting counts in words — [site/devmap.js:305-317](site/devmap.js). — [site/devmap.js](site/devmap.js)
- **The cost-by-category bar has no text equivalent**: "`bar.setAttribute('aria-hidden', 'true');`" — [site/devmap.js:215-216](site/devmap.js) — and its segments are pure colour with `flexGrow` set to the category's cost — [site/devmap.js:378-387](site/devmap.js). The legend counts beside it are *counts*, not cost — [site/devmap.js:376](site/devmap.js), [site/devmap.js:391](site/devmap.js) — so the cost split by category is available only visually, only as colour. — [site/devmap.js](site/devmap.js)
- **Specks carry category in colour alone**: "`nextSpecks.push({ p, color: catOf.get(projectCategory(p))?.color ?? '#9b958d' });`" — [site/devmap.js:944](site/devmap.js) — drawn as plain filled or dashed circles with no glyph — [site/devmap.js:746-769](site/devmap.js). — [site/devmap.js](site/devmap.js)
- **There are no clusters in this version.** `draw()` hard-codes "`node.dataset.clusters = '0';`" — [site/devmap.js:959](site/devmap.js) — `nextCluster` is created and assigned but never filled — [site/devmap.js:874](site/devmap.js), [site/devmap.js:954](site/devmap.js). The check's comment still describes them ("Pins are category icons or counted clusters" — [backend/test/browser/devmap-check.mjs:198](backend/test/browser/devmap-check.mjs)). Overlap is handled instead by the pill/speck split and, at zoom ≥ 16, by the `fan()` ring/spiral — [site/devmap.js:885-911](site/devmap.js). — [site/devmap.js](site/devmap.js)
- Other good details: the schedule bar is a named graphic — "`track.setAttribute('role', 'img'); track.setAttribute('aria-label', 'Estimated ${Math.round(pct)}% of the way from start to finish by today');`" — [site/devmap.js:1206-1208](site/devmap.js); the panel's close and step buttons have `aria-label`s rather than relying on the `‹ › ✕` glyphs — [site/devmap.js:1156-1172](site/devmap.js); the city chips are a labelled `role=group` with `aria-pressed` — [site/devmap.js:132-142](site/devmap.js); the search input has a long explicit `aria-label` and its decorative icon is `aria-hidden` — [site/devmap.js:190-198](site/devmap.js). — [site/devmap.js](site/devmap.js)
- The chip row and the phone city `select` never coexist in the accessibility tree — the pair is swapped with `display: none` at [site/style.css:8995-9001](site/style.css) and [site/style.css:9112-9118](site/style.css) — so there is no duplicate "City" control. — [site/style.css](site/style.css)
- Minor: the legend's accessible name embeds a pointer-specific instruction — "`legend.setAttribute('aria-label', 'Categories: click one to hide or show it');`" — [site/devmap.js:218](site/devmap.js); the same wording appears in the per-button `title` ("Hidden: click to show" / "Click to hide") — [site/devmap.js:393](site/devmap.js). The chart's note and bar labels likewise say "click a bar" — [site/devmap.js:609](site/devmap.js). — [site/devmap.js](site/devmap.js)
- Minor: `chart` is a `<section aria-label="Filings by month">` ([site/devmap.js:290-291](site/devmap.js)) whose content includes an `<h3>Filings by month</h3>` ([site/devmap.js:609](site/devmap.js)) — the `aria-label` wins and the heading is then unused for naming. — [site/devmap.js](site/devmap.js)

### Inferences
- The project list genuinely substitutes for reading pins *as data* — every located and unlocated project appears once, with its category named, its cost, and an explicit tag when it is not on the map. It does **not** substitute for the map's *spatial* information (clustering, which projects are near each other, which town a pin falls in beyond the `place` string). That is a reasonable limit, but the map region's label does not tell a non-visual user that the list is the equivalent, so the relationship has to be discovered.
- WCAG 1.4.1 Use of Colour (A) is satisfied for pins, legend, list and panel because of the glyph set, and a switched-off legend category also gets `text-decoration: line-through` plus muted text, not just a dimmed badge ([site/style.css:7827-7834](site/style.css)). It is *not* satisfied for the cost bar and for specks.
- WCAG 1.1.1 Non-text Content (A): hiding the cost bar with `aria-hidden` is legitimate only if the information is available elsewhere; the cost-by-category split is not, so this is a confirmed gap rather than a correct decorative-hiding.

### Gaps
- Whether a screen reader announces the Leaflet attribution control and zoom buttons intelligibly inside the labelled map region was not tested.

### Concrete fixes
1. State the alternative in the map's own name, e.g. `aria-label="Map of ${city} metro development projects — the same projects are listed in the Projects region"` at [site/devmap.js:287](site/devmap.js).
2. Give the cost bar a text equivalent instead of `aria-hidden`: keep the bar decorative but append a `.visually-hidden` sentence built from `byCost` ("Residential $1.2B, Office $840M, …") next to `.devx-total`. The `.visually-hidden` utility already exists — [site/style.css:151-158](site/style.css).
3. Reword the pointer-specific names: "Categories: choose one to hide or show it" ([site/devmap.js:218](site/devmap.js)) and "choose a bar to start there" ([site/devmap.js:609](site/devmap.js), [site/devmap.js:616](site/devmap.js)).
4. Drop the redundant `aria-label` on `chart` ([site/devmap.js:291](site/devmap.js)) and give the `h3` an id referenced by `aria-labelledby`, so the visible heading is the name.
5. Delete the dead cluster scaffolding (`nextCluster`, `clusterOf`, `dataset.clusters`) or restore it; the stale test comment at [backend/test/browser/devmap-check.mjs:198](backend/test/browser/devmap-check.mjs) is actively misleading about what the map draws.

## Screen reader: are dynamic updates announced?

### Takeaway
Exactly one live region exists — the result count — and it is well built, including a visually-hidden pin count. Everything else changes silently: selecting a project (the single biggest interaction on the page), the empty state, the "more in Smaller filings" hint, the cost total and the pin total.

### Cited findings
- The one live region: "`const count = el('p', 'dev-count'); count.setAttribute('aria-live', 'polite');`" — [site/devmap.js:239-240](site/devmap.js) — refreshed on every `apply()` with the filtered count, the "of N" qualifier when filters are active, and a hidden pin count: "`el('span', 'dev-count-pins visually-hidden', ' · ${pins} ${pins === 1 ? 'pin' : 'pins'} on the map')`" — [site/devmap.js:365-369](site/devmap.js). So filter, legend, sort, chart-month and search changes do produce an announcement. — [site/devmap.js](site/devmap.js)
- **Selecting a project is silent.** `select()` replaces the panel's children, unhides it and adds a class — "`panel.replaceChildren(...projectPanel(...)); panel.hidden = false; mapWrap.classList.add('panel-open');`" — [site/devmap.js:433-435](site/devmap.js) — with no live region, no focus move ([site/devmap.js:439](site/devmap.js), never reached) and no `aria-expanded` on the invoking row. ### Inferences
- Silent project selection is a confirmed failure. The cleanest citation is WCAG 2.4.3 Focus Order (A) via the missing focus move (see the previous section); if the panel is treated as a status rather than a destination, WCAG 4.1.3 Status Messages (AA) applies. - The empty state and the smaller-filings hint are textbook 4.1.3 (AA) failures: new content appears without focus moving and without a status role.
- `aria-live="polite"` on a 120 ms-debounced counter will queue and then collapse announcements in most screen readers, but on verbose settings it is noisy. A `role="status"` with the same debounce, or a longer debounce for the announcement only, would read better.

### Concrete fixes
1. Move focus into the panel on open (see previous section) — that alone fixes the announcement for the selection case without adding a region.
2. Put `empty` and `smallerHint` inside, or adjacent to, a `role="status"` container; or extend the existing `.dev-count` region's text to include "no projects match these filters — clear filters to see all N" when `shown.length === 0`.
3. Add `aria-expanded` to `.dev-pick` reflecting whether that row's project is the one open in the panel, so a row's state is discoverable before activating it.
4. Add an assertion to `devmap-check.mjs`: after a filter change and after a row click, a node with `aria-live`/`role=status` within `.dev-card` contains text naming the new count / the selected project.

## Motion: is `prefers-reduced-motion` honoured everywhere animation occurs?

### Takeaway
Nearly, and more thoroughly than the commit message suggests — the CSS has two overlapping *global* reduce blocks that kill every animation and transition on the page, and the JS has a `reduceMotion()` helper used at six of seven motion sites. The one miss is a hard-coded `behavior: 'smooth'` scroll. Note that the "glow off under reduced motion" commit (`b1d6b42`) is about the Events page cursor glow, not the map.

### Cited findings
- Two global CSS reduce blocks, either of which covers the whole map: "`@media (prefers-reduced-motion: reduce) { *, *::before, *::after { animation: none !important; transition: none !important; } }`" — [site/style.css:2211-2218](site/style.css) — and a second with `animation-duration: 0.01ms !important`, `animation-iteration-count: 1 !important`, `transition-duration: 0.01ms !important`, `scroll-behavior: auto !important` — [site/style.css:7584-7592](site/style.css). — [site/style.css](site/style.css)
- Two further map-specific blocks, now redundant but harmless: `.devx-pin { transition: none; }` — [site/style.css:8036-8040](site/style.css) — and the selection pulse, which is also frozen at a fixed scale rather than merely stopped: "`.devx-pulse { animation: none; transform: scale(0.8); }`" — [site/style.css:8309-8314](site/style.css), where the live rule is `animation: devx-pulse 1.6s ease-out infinite` — [site/style.css:8286-8295](site/style.css). — [site/style.css](site/style.css)
- The JS helper: "`function reduceMotion() { return Boolean(window.matchMedia?.('(prefers-reduced-motion: reduce)').matches); }`" — [site/devmap.js:508-510](site/devmap.js) — and it is checked at the phone "to list" scroll ([site/devmap.js:200](site/devmap.js)), the list's auto-scroll to the selected row ([site/devmap.js:431](site/devmap.js)), the stacked-layout scroll back to the map ([site/devmap.js:438](site/devmap.js)), the speck click zoom-in (`{ animate: !reduceMotion() }` — [site/devmap.js:783](site/devmap.js)), `openSmall`'s flight (`duration: reduceMotion() ? 0 : 0.6` — [site/devmap.js:1006](site/devmap.js)) and `select`'s flight (`if (reduceMotion()) map.setView(target, zoom, { animate: false }); else map.flyTo(target, zoom, { duration: 0.6 });` — [site/devmap.js:1053-1054](site/devmap.js)). — [site/devmap.js](site/devmap.js)
- **The one confirmed miss**: the smaller-filings hint scrolls with a hard-coded smooth behaviour — "`details.scrollIntoView({ block: 'start', behavior: 'smooth' });`" — [site/devmap.js:259-265](site/devmap.js). Every comparable call in the file is guarded; this one is not. The CSS `scroll-behavior: auto !important` at [site/style.css:7590](site/style.css) does **not** override an explicit `behavior: 'smooth'` passed to `scrollIntoView` — the option takes precedence over the computed property. — [site/devmap.js](site/devmap.js)
- `fit()` never animates regardless of preference (`{ ...padding(), animate: false }` and `map.setView(..., { animate: false })`) — [site/devmap.js:972-978](site/devmap.js). — [site/devmap.js](site/devmap.js)
- Leaflet's own animation options are not set: `L.map(node, { scrollWheelZoom: true, zoomControl: false })` — [site/devmap.js:669](site/devmap.js) — so `zoomAnimation`, `fadeAnimation` and `markerZoomAnimation` keep their defaults (`true`) and user-initiated zooms (zoom control, wheel, double-tap) animate even under reduce. — [site/devmap.js](site/devmap.js)
- **The check never emulates reduced motion.** `page.emulateMedia` / `prefers-reduced-motion` appear nowhere in [backend/test/browser/devmap-check.mjs](backend/test/browser/devmap-check.mjs); contexts are created with only viewport, `isMobile`, `hasTouch` and `deviceScaleFactor` — [backend/test/browser/devmap-check.mjs:140](backend/test/browser/devmap-check.mjs). — [backend/test/browser/devmap-check.mjs](backend/test/browser/devmap-check.mjs)

### Inferences
- Motion coverage is good, so WCAG 2.3.3 Animation from Interactions (AAA) is close to met; the smooth scroll at [site/devmap.js:263](site/devmap.js) is a confirmed single-line failure of it.
- The infinite 1.6 s selection pulse would engage WCAG 2.2.2 Pause, Stop, Hide (A) were it not reduced-motion-aware and arguably essential (it marks the current selection); with the reduce rule in place and `interactive: false` ([site/devmap.js:828](site/devmap.js)) this is low risk.
- **Needs a browser:** the blanket `transition: none !important` at [site/style.css:2213-2216](site/style.css) removes the CSS transitions Leaflet's zoom animation relies on for its `transitionend`. The file already documents a related hazard — "Leaflet 1.9 ends a zoom animation with an untracked 250 ms timer that reads the map's panes; once remove() has deleted them that timer throws" — [site/devmap.js:85-93](site/devmap.js). That 250 ms fallback probably means zooms still complete under reduce, but a stuck `_animatingZoom` (blank pane, dead map) is the plausible failure mode and must be checked on a real page with reduced motion forced.

### Concrete fixes
1. One-line fix at [site/devmap.js:263](site/devmap.js): `behavior: reduceMotion() ? 'auto' : 'smooth'`.
2. Pass Leaflet the preference at construction: `L.map(node, { scrollWheelZoom: true, zoomControl: false, zoomAnimation: !reduceMotion(), fadeAnimation: !reduceMotion(), markerZoomAnimation: !reduceMotion() })` at [site/devmap.js:669](site/devmap.js). This also removes the `transition: none !important` interaction risk above.
3. Add a reduced-motion pass to the check: a context with `reducedMotion: 'reduce'` that opens the map, zooms twice via the zoom control and asserts the map still renders pins and `.dev-map` has no `leaflet-zoom-anim` class left on it.

## Colour and contrast on the night basemap

### Takeaway
The "night basemap" is **not** theme-conditional — the tile inversion and the dark pins/pills apply in light mode too, so the map always presents as dark whatever the site theme. Within that dark map, contrast is handled well (the price pills are near-maximum contrast). The real contrast risks are *outside* the map: the accent-coloured panel category line and the Clear-all pill in light theme compute to roughly 4.4:1, and some white category glyphs sit close to the 3:1 non-text line.

### Cited findings
- The night basemap has no media query or theme selector around it: "`/* Night basemap: OpenStreetMap tiles darkened in the browser, no extra tile service. */ .devx .leaflet-tile-pane { filter: invert(1) hue-rotate(180deg) brightness(0.82) contrast(0.92) saturate(0.6); }`" and "`.devx .leaflet-container { background: #16140f; }`" — [site/style.css:8022-8030](site/style.css). An `awk` scan for `@media`/`@supports` between lines 7700 and 8030 of `style.css` returns nothing, so these rules are unconditional. — [site/style.css](site/style.css)
- The map furniture is likewise hard-coded dark, not tokenised: `.devx-pin` is a radial gradient onto `#16140f` with `box-shadow: 0 2px 6px oklch(0 0 0 / 0.45)` — [site/style.css:7895-7910](site/style.css); `.devx-pill` is `color: #f3efe8; background: #16140f` — [site/style.css:7934-7950](site/style.css); the chosen pill flips to `color: #16140f; background: #f3efe8` with a 3 px `var(--accent)` ring — [site/style.css:7986-7994](site/style.css); the leader lines are `stroke: #1b1917` — [site/style.css:8032-8035](site/style.css). — [site/style.css](site/style.css)
- **Price pills pass comfortably.** `#f3efe8` on `#16140f` is roughly 15:1 — far above the 4.5:1 that WCAG 1.4.3 (AA) asks of 12.5 px/600 text ([site/style.css:7940-7944](site/style.css)). The pin key's sample pill uses the same pair — [site/style.css:8069-8077](site/style.css) — and is `aria-hidden` anyway ([site/devmap.js:280](site/devmap.js)). — [site/style.css](site/style.css)
- **Category glyphs on badges are near the 3:1 line.** `.devx-cat { --glyph: #ffffff; background: var(--cat); color: var(--glyph); }` — [site/style.css:7836-7840](site/style.css) — with `.devx-glyph-dark { --glyph: #1b1917; }` for `industrial` and `other` — [site/style.css:7842-7845](site/style.css), [site/devicons.js:25](site/devicons.js). The category colours are `residential #d27a52`, `office #6874c8`, `industrial #c9a347`, `healthcare #c46a92`, `public #4f9a7e`, `retail #4c9cbf` — [site/market.js:347-355](site/market.js) — and `other #9b958d` — [site/market.js:355](site/market.js). White on `retail #4c9cbf` computes to roughly **2.9:1** and white on `residential #d27a52` to roughly **3.4:1**; the 3:1 threshold of WCAG 1.4.11 Non-text Contrast (AA) applies to these glyphs. Badges are 22 px with a 14 px glyph — [site/style.css:7847-7858](site/style.css). — [site/market.js](site/market.js)
- **Accent text in light theme is marginal.** `--accent: oklch(var(--acc-l) 0.15 var(--acc-h))` with `--acc-l: 0.57` on `--surface: #ffffff` — [site/style.css:4-28](site/style.css) — computes to roughly **4.4:1**, i.e. just under 4.5:1. It is used for 13 px panel category text — "`.devx-panel-cat { font-size: 13px; color: var(--accent); }`" — [site/style.css:8575-8582](site/style.css) — and for the Clear-all pill label at 13.5 px — "`.devx-clear { color: var(--accent); }`" — [site/style.css:8390-8392](site/style.css), [site/style.css:8338-8343](site/style.css). In dark theme `--acc-l` rises to 0.7 ([site/style.css:63](site/style.css), [site/style.css:88](site/style.css)), which clears the bar. — [site/style.css](site/style.css)
- Muted body text passes in both themes: `--muted` is `oklch(0.5 0.005 60)` on white (≈4.6:1) and `oklch(0.66 0.003 80)` on `--surface: oklch(0.175 0.009 50)` (≈6.9:1) — [site/style.css:12](site/style.css), [site/style.css:58](site/style.css). It carries `.devx-panel-note`/`.devx-panel-loc` at 12.5 px — [site/style.css:8617-8627](site/style.css) — and the chart axis at **11 px** — [site/style.css:8521-8526](site/style.css), which passes contrast but is very small type. — [site/style.css](site/style.css)
- Switched-off legend categories do not rely on colour: `.devx-legend-item[aria-pressed='false'] { color: var(--muted); text-decoration: line-through; }` plus `opacity: 0.25` on the badge — [site/style.css:7827-7834](site/style.css). — [site/style.css](site/style.css)
- Chart bar state is colour-coded (`var(--ink2)` default, `var(--accent)` when pressed, `var(--line)` for months before the cut) — [site/style.css:8505-8520](site/style.css) — but each bar also carries `aria-pressed` and a full `aria-label` — [site/devmap.js:615-617](site/devmap.js) — so 1.4.1 is met programmatically. — [site/style.css](site/style.css)
- Filter pill borders are `1px solid var(--line)` where `--line` is `oklch(0.19 0.005 60 / 0.1)` — about 1.1:1 against white — [site/style.css:13](site/style.css), [site/style.css:8338-8343](site/style.css). They sit on `var(--shadow-float)` over the map, which is what actually separates them. — [site/style.css](site/style.css)
- **The check measures no colour at all** — no contrast, no theme switch; every context runs the default (light or OS) theme — [backend/test/browser/devmap-check.mjs:136-141](backend/test/browser/devmap-check.mjs). — [backend/test/browser/devmap-check.mjs](backend/test/browser/devmap-check.mjs)

### Inferences
- Because the map is permanently dark, the question "do the price pills meet contrast on the night basemap" has one answer in both themes, and it is yes. The theming work did not extend to making the map *follow* the theme; light-theme users get an always-dark map inset into a white card. That is a large luminance jump across the panel boundary but not a WCAG failure.
- The accent-on-white ratios are a *probable* 1.4.3 (AA) failure in light theme and the single most likely real contrast defect on this screen. Raising `--acc-l` for text use would touch the whole site, so the map-local fix is to use `--on-tint: oklch(0.45 0.13 var(--acc-h))` ([site/style.css:27](site/style.css)), which the token set already provides for exactly this purpose.
- Colour is not the only carrier of category meaning anywhere a user can read it — glyphs cover pins, badges, legend, list and panel. The exceptions are the `aria-hidden` cost bar and the canvas specks (see the Semantics section).

### Gaps
- Every ratio above is computed from the OKLCH/hex values by hand. They need confirming with a real contrast tool against the rendered page — in particular `--accent` on `--surface` (is it 4.4 or 4.5?) and white on `#4c9cbf`.
- **Needs a browser:** the cascade on pins. `.devx-cat` sets `color: var(--glyph)` at [site/style.css:7839](site/style.css) while `.devx-pin` sets `color: color-mix(in srgb, var(--cat) 82%, #ffffff)` at [site/style.css:7899](site/style.css); both are single-class selectors, so the later `.devx-pin` should win and `DARK_GLYPH` should have no effect on *pins* (only on `.devx-badge`, which sets no colour of its own). If that reading is wrong, `industrial` and `other` pins would draw a near-black `#1b1917` glyph on a near-black disc — effectively invisible. Worth checking first, as it is cheap and the consequence is severe.
- Whether the inverted tiles themselves keep enough contrast for street labels at the darkened `brightness(0.82) contrast(0.92) saturate(0.6)` settings cannot be judged from source.

### Concrete fixes
1. Swap `var(--accent)` for `var(--on-tint)` in `.devx-panel-cat` ([site/style.css:8580](site/style.css)) and `.devx-clear` ([site/style.css:8391](site/style.css)), or raise those to 14 px/600 so the 3:1 large-text threshold applies.
2. Darken `retail` and `residential` (and check `public`, `healthcare`) in `DEV_CATEGORIES` ([site/market.js:347-355](site/market.js)) until white-on-colour clears 3:1, or add them to `DARK_GLYPH` ([site/devicons.js:25](site/devicons.js)) so their badges use the `#1b1917` glyph.
3. Raise the chart axis from 11 px ([site/style.css:8524](site/style.css)) to 12 px to match the rest of the card's small type.
4. Either wrap the night-basemap rules at [site/style.css:8022-8030](site/style.css) in `:root[data-theme='dark'], @media (prefers-color-scheme: dark)` and build a light pin/pill set, or leave them unconditional and add a comment saying the map is deliberately dark in both themes — right now the rule's name ("Night basemap") implies a conditionality the selector does not have.
5. Add a contrast pass to the check: run it once with `colorScheme: 'light'` and once with `'dark'`, and assert computed ratios for `.devx-pill b`, `.devx-panel-cat`, `.devx-clear`, `.devx-axis` and the badge glyphs.

## Responsive behaviour at phone widths

### Takeaway
The phone layout has had real attention — a dedicated workspace height, a scrolling filter row, a bottom sheet, and a purpose-built "Search & project list" button — and `devmap-check.mjs` already asserts no horizontal page scroll, legend labels not clipped, and the last filter pill reachable. ### Inferences
- The `order: -1` inversion is a confirmed failure of WCAG 1.3.2 Meaningful Sequence (A) and 2.4.3 Focus Order (A): the reading/focus order below 900 px no longer matches the presentation order, and the `.devx-to-list` button is a mitigation for sighted keyboard users rather than a fix. Moving the map before the side column in the DOM and reversing the desktop grid with `order`/`grid-column` instead would fix both at once — the DOM order would then be map-then-list, which is also the better screen-reader order (the map region, then its text equivalent).
- The chart bar width is a confirmed 2.5.8 failure by computation; only the exact month count (from `filingsByMonth`, see [site/devmap.js:396](site/devmap.js)) is unknown, and more months makes it worse, never better.
- Hiding the filters while the sheet is open is a functional regression rather than a named WCAG failure, but combined with the missing focus move it means a phone user who opens a project has no filter controls and no focus anywhere predictable.

### Gaps
- **Needs a browser:** whether the phone sheet covers the OSM attribution control. Leaflet's attribution is a licence requirement as well as an accessibility one, and the sheet's `z-index: 600` and `bottom: 6px` make covering it likely.
- **Needs a browser:** whether the `calc(100dvh - 56px - 8px - 124px - 60px)` map height clips below the fixed tabs when the title row wraps (long city name + Follow button + "Search & project list" on a 320 px viewport), outside the `data-workspace="map"` case where `fitWorkspace()` corrects it.
- **Needs a browser:** whether the `position: fixed` More popover at [site/style.css:8840-8843](site/style.css) lands on screen, and whether its contents are reachable when it overlaps the bottom tab bar.
- No 400 % zoom / 320 px reflow pass exists (WCAG 1.4.10); the check's narrowest viewport is 390 px.

### Concrete fixes
1. Reverse the source order: append `mapWrap` before `side` at [site/devmap.js:186](site/devmap.js) and restore the desktop left-column layout with `order`/`grid-template-areas` in `.devx-body` ([site/style.css:7700-7706](site/style.css)), then drop `order: -1` at [site/style.css:8800](site/style.css). This removes the inversion in both reading and focus order and makes `.devx-to-list` a convenience rather than a necessity.
2. Give `.devx-bar-col` a usable target: either `min-width: 24px` with the row scrolling horizontally on phones, or collapse to quarters/half-years under 640 px, or move month selection to a `select` on phones and keep the bars as a `role="img"` chart with a text summary.
3. Add `min-height: 24px` (ideally 32) to `.devx-seg-item` at [site/style.css:8117](site/style.css), and lift `.devx-panel-nav .icon-button` ([site/style.css:8589](site/style.css)) and the phone footer buttons ([site/style.css:9098](site/style.css)) toward 44 px on touch pointers via `@media (pointer: coarse)`.
4. Keep the filter row available with the sheet open — drop `.devx-filters` from the `display: none` rule at [site/style.css:8561](site/style.css) and let the sheet start below it — or add a "Filters" button inside the sheet head.
5. Raise the sheet's `bottom` above the Leaflet attribution and zoom control on phones, or move those controls to `topright` while `.narrow.panel-open`.
6. Replace the hand-computed `calc()` heights at [site/style.css:9043-9067](site/style.css) with the measured `fitWorkspace()` path for all narrow cases (not only `data-workspace="map"`), or add `max-height: calc(100dvh - <measured top>)` so a wrapped title row can never push the map under the tabs.
7. Give the scrolling filter row and city chip row a visible overflow affordance (an edge fade, or `scrollbar-width: thin` on `pointer: fine`), since `scrollbar-width: none` currently hides the only cue that more filters exist.
8. Extend the check with a 320 px viewport and a 400 % zoom case, and add target-size assertions (every control inside `.dev-card` has a bounding box ≥ 24×24).
