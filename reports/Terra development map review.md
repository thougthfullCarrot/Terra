# Terra's dev map loses state users built

Terra's development map is the `tool=map` workspace of the Markets section: one card, built by `developmentMap()` in [site/devmap.js](site/devmap.js) and hosted only by [site/markets-view.js](site/markets-view.js), reached through `#markets&tool=map&city=<metro>` from the metro side panel, the development teaser card, or a pasted hash. It draws a Leaflet night map over a project dock (search, legend, sort, list), a filing chart and a detail panel, from a two-stage data load: `market.json` carries each metro's headline projects, and `developments/<slug>.json` carries that metro's full list, fetched on open. **The single highest-consequence defect is that the full-list arrival calls `render()`, which disposes the Leaflet map and rebuilds the card from scratch a few seconds after the user arrives — destroying their viewport, list scroll and open project — and the same two-stage path swallows a fetch failure into a `'failed'` flag nothing reads, leaving a silently truncated map that looks authoritative.** Around that sit four more live correctness bugs, three of which are one-line or near-one-line fixes: every user filter change still force-refits the map although the `keepView` mechanism to stop it now exists and is used by the time-lapse; a metro switch with a stale filter renders zero results with every pill reading "All"; "Clear all" neither resets the sort nor stops a running time-lapse; and focus never moves into the detail panel, so the phone sheet opens over the map with focus left behind. Recent work has genuinely landed — the duplicate Leaflet integration is gone, canvas reallocation and per-project color lookups are memoised, and the phone DOM-order inversion is fixed — but the newest feature, the time-lapse, arrived with no test coverage at all, and the browser check's slow-phone block measures four quantities and asserts none of them.

All line numbers below are current at HEAD `8897046` (`site/devmap.js` 1599 lines, `site/markets-view.js` 1165, `backend/test/browser/devmap-check.mjs` 723), taken from the verification pass that re-checked every earlier finding against this tree.

## Six live correctness bugs, three of them one-line fixes

**1. The stage-2 arrival rebuilds the card mid-interaction.** When `developments/<slug>.json` resolves, the loader replaces that city's rows in the shared snapshot and calls `render()` — `data.projects = [...data.projects.filter((p) => p.city !== city), ...file.projects]; devFiles.set(city, 'done'); render();` ([site/markets-view.js:1041-1048](site/markets-view.js#L1041-L1048)). `render()` begins with `disposeMap()` ([site/markets-view.js:232](site/markets-view.js#L232)) and then `$('m-body').replaceChildren(devMap(state.city || null, true) || mapMissing())` ([site/markets-view.js:238](site/markets-view.js#L238)), so the whole card, its Leaflet map and its entire row set are built twice on every first open of a metro. `filters`, `sort` and `hiringOnly` survive because they are module globals ([site/devmap.js:61](site/devmap.js#L61), [:106](site/devmap.js#L106), [:108](site/devmap.js#L108)); `selected` is card-local (set in `select()` at [site/devmap.js:550](site/devmap.js#L550)), as are the list scroll, the viewport and any running time-lapse. A user who clicks a pin on arrival watches the panel vanish. This is not a one-liner: `items` is keyed by the project *object* ([site/devmap.js:1328-1366](site/devmap.js#L1328-L1366)) while the loader replaces those objects wholesale, so identity cannot survive a merge. The bounded fix is to carry `selectedId` (rows already hold `project.id`) and the viewport across the rebuild, or merge the arriving rows into the existing card instead of re-rendering.

**2. A failed stage-2 fetch is invisible and never retried.** `.catch(() => devFiles.set(city, 'failed'))` ([site/markets-view.js:1050](site/markets-view.js#L1050)) is the whole error path, and `'failed'` is read nowhere — `devFiles` appears only at [:55](site/markets-view.js#L55), [:75](site/markets-view.js#L75), [:1036-1037](site/markets-view.js#L1036-L1037), [:1043](site/markets-view.js#L1043), [:1047](site/markets-view.js#L1047) and [:1050](site/markets-view.js#L1050). The retry guard `if (!path || devFiles.has(city)) return;` ([site/markets-view.js:1036](site/markets-view.js#L1036)) then blocks any later attempt, and the loader's perfectly good message `throw new Error(\`${path} returned ${response.status}\`)` ([site/markets-view.js:60](site/markets-view.js#L60)) is discarded. The user sees the headline set only — 300–400 projects out of possibly thousands — with a live count that reads as authoritative, correct-looking pins and a correct-looking coverage note. A renamed slug, a broken path or a Supabase RLS change produces a quietly wrong map. The fix is about ten lines: on failure, `render()` as well as recording `'failed'`, and have the card show a `stateBox('Some of this metro's projects could not be loaded…', 'error')` when the host passes `partial: true`. The right pattern already exists one file away for the top-level snapshot ([site/markets-view.js:180](site/markets-view.js#L180)).

**3. Every user filter change still throws away the user's pan and zoom — and the fix is now one word.** `show()` has gained an opt-out, `show(ids, { keepView = false } = {}) { … if (keepView && fitted) draw(); else fit(); }` ([site/devmap.js:1241-1253](site/devmap.js#L1241-L1253)), but the only call site passes it for the time-lapse alone: `map?.show(ids, { keepView: Boolean(until) })` ([site/devmap.js:488](site/devmap.js#L488)). For an ordinary filter change, keystroke, legend click, chart click, sort or hiring toggle, `until` is `''` and `fit()` runs, unconditionally `fitBounds`/`setView` ([site/devmap.js:1203-1208](site/devmap.js#L1203-L1208)); the `fitted` flag only suppresses a second ResizeObserver fit ([:1216](site/devmap.js#L1216)). So each search keystroke re-zooms the map out from under the user. **This is the highest user-visible win in the review for the smallest diff**: pass `keepView: true` for user-driven changes and keep `fit()` for a city change or the first non-empty result (`if (!fitted || cityChanged) fit()`). The mechanism is already shipped and exercised by the lapse.

**4. Switching metros with a stale filter gives zero results and no explanation.** Only `place` resets on a city change — `if (filtersCity !== city) { filters = { ...filters, place: '' }; filtersCity = city; }` ([site/devmap.js:165-168](site/devmap.js#L165-L168)) — so `cost`, `work`, `publicInvolvement`, `status`, `filed`, `since`, `off`, `query`, `sort` and `hiringOnly` all carry across. `apply()` computes results first (`const shown = lapse(hiring(filterProjects(all, filters, asOf)))` — [site/devmap.js:389](site/devmap.js#L389)) and reconciles the pills last, via `pills.badge(...)` ([:485](site/devmap.js#L485)) whose final statement is `api.sync()` ([:723](site/devmap.js#L723)). `sync()` then drops the unmatched value with no re-render, with the case acknowledged in its own comment ([site/devmap.js:713-720](site/devmap.js#L713-L720)). Filter Austin by `Status = Pending`, switch to El Paso: the final frame is zero results with every pill reading "All", and nothing on screen explains what is filtering. Fix: reconcile the pills against `filterChoices(all)` before computing `shown` — move the prune step to just after the `filtersCity !== city` block — or have `sync()` call `apply()` when it drops a value.

**5. "Clear all" is an incomplete escape hatch, and the time-lapse makes it worse.** `clearAll()` resets `filters` and `hiringOnly` only ([site/devmap.js:378-383](site/devmap.js#L378-L383)): `sort` survives, is not counted as an active filter, and so cannot be restored to "Biggest" by any visible control. Worse, the time-lapse's `until` ([:371](site/devmap.js#L371)) and `lapseTimer` ([:372](site/devmap.js#L372)) are untouched too, so "Clear all" during a running lapse leaves the interval running and the result set still capped by `until` ([:377](site/devmap.js#L377)) while every pill reads "All" — the same user-facing shape as bug 4, from a different cause. And because `until` is not part of `filters`, `active = activeFilterCount(filters) + (hiringOnly ? 1 : 0)` ([:417](site/devmap.js#L417)) does not see it, so `clear.hidden = !active` ([:721](site/devmap.js#L721)) *hides the escape hatch* while the lapse is restricting the set, and the count renders "N projects" without the "of M" qualifier ([:419-424](site/devmap.js#L419-L424)). The `lapseChip` ([:373-374](site/devmap.js#L373-L374)) is the only indication anything is restricted. Two near-one-line fixes: add `sort = 'biggest'` and `stopLapse()` to `clearAll()`, and fold `until` into the active-filter count.

**6. Leaving the Markets tab tears nothing down, and a playing time-lapse keeps burning CPU.** `show()` hides the markets section and returns before any teardown — `for (const name of ['jobs', 'markets', 'tracker']) $(\`${name}-view\`).hidden = name !== active; … if (!open) { delete document.body.dataset.workspace; return; }` ([site/markets-view.js:154-165](site/markets-view.js#L154-L165)). `disposeMap()` is called only from `setMarketLoader` ([:76](site/markets-view.js#L76)) and the top of `render()` ([:232](site/markets-view.js#L232)), neither of which runs on a tab change. So the Leaflet map, its `zoomend moveend` redraw ([site/devmap.js:1199](site/devmap.js#L1199)), two `click` handlers ([:989](site/devmap.js#L989), [:1032](site/devmap.js#L1032)), a `mousemove` handler ([:996](site/devmap.js#L996)), the speck canvas and the ResizeObserver all stay live on a hidden subtree. **The amplifier is the time-lapse**: its tick guard is `if (!box.isConnected) return clearInterval(lapseTimer)` ([site/devmap.js:506-517](site/devmap.js#L506-L517)), written for the city-change case ("Another city's map replaced this one"), but the tab-away path *hides* rather than detaches, so a lapse left playing keeps running `apply()` — four `filterProjects` sweeps of the metro — plus `map.blip()` marker churn every 280 ms on an invisible tab. Half of this is a genuine one-liner: call `disposeMap()` before the `return` in the `!open` branch; it is already imported and idempotent. The lapse needs the card to expose a `destroy()` that runs `stopLapse({ redraw: false })`, clears the search debounce ([:247](site/devmap.js#L247)), bumps `listTurn` and calls `disposeMap()`. The cheap stopgap — `box.isConnected && !box.closest('[hidden]')` — treats the symptom. The deeper point is that three separate guards (`node.isConnected` at [:838](site/devmap.js#L838), `box.isConnected`, and `map !== liveMap` in eight places) each encode an assumption about the host that the host does not state.

## Design and maintainability: the state split, two 500-line functions, and dead clustering residue

Nothing in this section is broken. The structural problem is that **there is no single source of truth**: `filters`, `sort` and `hiringOnly` are module-level mutable globals that outlive any card ([site/devmap.js:58-62](site/devmap.js#L58-L62), [:106](site/devmap.js#L106), [:108](site/devmap.js#L108)), while `selected`, `order`, `until` and `lapseTimer` are closure-local to one `developmentMap()` call ([:371-372](site/devmap.js#L371-L372)) and the viewport lives only inside Leaflet. The DOM holds a second copy of the query (`input.value = filters.query` rewritten every pass, [:387](site/devmap.js#L387)), the map a third derived copy plus a string fingerprint ([:1245-1247](site/devmap.js#L1245-L1247)), and `filterPills.sync()` repairs the globals *by writing to them from inside a render function* ([:713-720](site/devmap.js#L713-L720)). That split is what makes bugs 1 and 4 above structural rather than incidental. The bounded change the notes propose is one `devMapState` object (`{ filters, sort, hiringOnly, selectedId, until, view }`) created by the host and passed into `developmentMap({ state })`, with the first half of `apply()` extracted as a pure `(all, state, asOf) → viewModel`; that removes `sync()`'s write-back, lets selection survive a refresh keyed by `project.id`, and makes the derive step testable without a DOM.

**Two functions hold 62% of the file**, both having grown with the perf and time-lapse work: `developmentMap` is 517 lines ([site/devmap.js:117-633](site/devmap.js#L117-L633)) covering the title row, city switcher, global filter reconciliation, data derivation, search debounce, summary/cost bar/legend, sort segment, list and empty state, the coverage-note prose, `apply()` itself ([:386-491](site/devmap.js#L386-L491)), the entire time-lapse engine ([:497-527](site/devmap.js#L497-L527)), `select`/`step`/`close`, the Escape handler and the async map boot. `drawMap` is 478 ([:836-1313](site/devmap.js#L836-L1313)). Every extractable piece of pure logic is written as a closure over mutable locals, so none of it is reachable from a unit test — and the precedent for the alternative is in the same import list, since `filterProjects`, `sortProjects`, `filingsByMonth`, `projectCategory`, `filterChoices` and `activeFilterCount` already live in `market.js` behind a typed contract ([site/market.d.ts:115-120](site/market.d.ts#L115-L120)). The five extractions worth doing are each independently shippable and DOM-free: `packPills`, `fanOffsets(n)`, `fitPadding({w, h, open, narrow})`, `coverageNote(all, city, asOf)`, and — best of the five — `lapseEngine(months, { onTick, interval })`, because pulling the lapse out of a 517-line DOM builder is also what makes its teardown fixable in one place. `drawChart`'s six positional parameters, two of them nullable callbacks ([:748](site/devmap.js#L748)), should become an options bag before a seventh arrives.

**Delete the clustering residue.** Clustering was superseded by price-pill overlap packing, and four unread remnants survive: `const CELL = 64;` ([site/devmap.js:806](site/devmap.js#L806)), `let clusterOf = new Map();` with a comment still claiming it holds "the cluster each project sat in at the last draw" ([:1043-1044](site/devmap.js#L1043-L1044)), `const nextCluster = new Map();` which is never written ([:1095](site/devmap.js#L1095), assigned at [:1186](site/devmap.js#L1186)), and the hardcoded `node.dataset.clusters = '0'` ([:1191](site/devmap.js#L1191)). `speckAt` uses its own literal `let bestD = 64;` ([:982](site/devmap.js#L982)) rather than `CELL`. **A caution for that cleanup**: the rest of the `dataset.*` family — `pins`, `drawn`, `specks`, `smallPins`, `matches`, `drawMs` — is a de facto test contract read by the browser check and must not be removed; `clusters` is the only member nothing reads. The stale vocabulary has also leaked into the check itself, where the comment at [backend/test/browser/devmap-check.mjs:198](backend/test/browser/devmap-check.mjs#L198) still describes "counted clusters" and [:371](backend/test/browser/devmap-check.mjs#L371) reads `dataset.specks` into a variable named `clusters`. Alongside it: `toggleDetail` ([site/devmap.js:1385](site/devmap.js#L1385)) and `dueDate`'s export ([:1576](site/devmap.js#L1576)) have no consumers repo-wide, `panel.prevStep` ([:602](site/devmap.js#L602)) has no reader, and there is still no `site/devmap.d.ts` although sibling modules including `insights-view.d.ts` have one. Writing that `.d.ts` is what would force the `developmentMap` option bag to be named — the same object the state refactor would change, so the two land together. Moving `CENTERS` out to `market.js` (two import edits; `deal-view.js` imports a map-rendering module purely for `Object.keys(CENTERS)`, [site/deal-view.js:9,13](site/deal-view.js#L9-L13)) is a prerequisite for a clean one. Explicitly *not* worth doing: extracting a shared map-lifecycle helper. With `property-view.js` retired there is one Leaflet integration, and the abstraction would have a single caller.

On performance, three O(N)-per-pass costs survive and now matter more than when they were written, because the time-lapse runs `apply()` on a 280 ms interval ([site/devmap.js:516](site/devmap.js#L516)) with no user input: the change-detection bitstring `const key = projects.map((p) => (ids.has(p) ? 1 : 0)).join('');` ([:1245](site/devmap.js#L1245)), three `filterProjects` sweeps per `apply()` plus a fourth `lapse()` pass while playing ([:389](site/devmap.js#L389), [:391](site/devmap.js#L391), [:393](site/devmap.js#L393)), and a re-allocated re-sort of `shown` by cost on *every draw*, i.e. per pan and zoom ([:1157](site/devmap.js#L1157)), now joined by two further per-draw passes ([:1136](site/devmap.js#L1136), [:1139-1143](site/devmap.js#L1139-L1143)). Alongside them, `drawList` builds a `<li>` for every project in the metro eagerly before any filter runs ([:364](site/devmap.js#L364), `drawList` at [:1328](site/devmap.js#L1328)) — paid twice because of the stage-2 re-render — and `select()` sweeps the whole `items` map plus a `querySelectorAll` over the list, then reads `row.offsetTop`/`list.scrollTop` immediately after those writes ([:551-561](site/devmap.js#L551-L561)) and `mapWrap.getBoundingClientRect().top` immediately after `panel.replaceChildren` and `classList.add('panel-open')` ([:563-568](site/devmap.js#L563-L568)); `close()` runs two more full sweeps ([:587-588](site/devmap.js#L587-L588)). A remembered previous-selection reference removes all of that traversal. None of these is profiled — they are claims about algorithmic shape — and `dataset.drawMs` is already written ([:1193](site/devmap.js#L1193)) and would settle the question if anything read it. Two cheaper data-loading wins sit outside the map: `cache: 'no-cache'` on both fetches ([site/app.js:949](site/app.js#L949), [site/markets-view.js:59](site/markets-view.js#L59)) forces a re-download on every nightly ETag change, and the per-metro file has no cap at all while the build itself anticipates "about 4,000 a year" from Harris County alone.

## Accessibility and touch targets beyond the focus bugs

Three items here are design gaps rather than defects, and they are cheap. The cost-by-category bar is `aria-hidden` ([site/devmap.js:255](site/devmap.js#L255)) and built from `byCost` as colour segments alone ([:433-442](site/devmap.js#L433-L442)), while the legend's per-category numbers are *counts*, not cost ([:439](site/devmap.js#L439)) — so the cost split is conveyed by colour only, which makes the `aria-hidden` a real 1.1.1 gap rather than correct decorative hiding. A `.visually-hidden` sentence built from `byCost` next to `.devx-total` closes it with the utility the stylesheet already provides. Two touch targets fail WCAG 2.5.8 (24×24 AA) by computation: `.devx-bar-col { flex: 1; … padding: 0; }` with no `min-width` ([site/style.css:8499-8509](site/style.css#L8499-L8509)) gives month bars roughly 9–22px of width across 24 months on a 390px viewport, 3px apart; and `.devx-seg-item { padding: 4px 10px; font: 400 12.5px var(--ui); }` with no `min-height` ([site/style.css:8120-8128](site/style.css#L8120-L8128)) computes to about 25px. Adding `min-height: 24px` to the sort buttons is a one-line fix; the chart bars need a design call (a `min-width` with horizontal scroll, coarser buckets on phones, or a `select` for month choice).

The "night basemap" is **not theme-conditional**: `.devx .leaflet-tile-pane { filter: invert(1) … }` and `.devx .leaflet-container { background: #16140f; }` sit in no `@media` block and carry no `[data-theme]` selector ([site/style.css:8025-8031](site/style.css#L8025-L8031)), so light-theme users get an always-dark map inset into a white card. That is not a WCAG failure — the price pills clear contrast comfortably against the dark basemap in both themes — but the rule's name implies a conditionality the selector does not have, and either wrapping it in a dark-theme guard with a light pin set, or committing to it in a comment, resolves the ambiguity. The contrast risks are outside the map and **need measurement with a real tool rather than hand-computed OKLCH**: `var(--accent)` on white computes to roughly 4.4:1 for the 13px panel category line ([site/style.css:8581-8588](site/style.css#L8581-L8588)) and the Clear-all pill label ([:8401-8403](site/style.css#L8401-L8403)), marginally under 4.5:1 — the token set already ships `--on-tint` for exactly this; and white glyphs on `retail #4c9cbf` and `residential #d27a52` ([site/market.js:370](site/market.js#L370), [:375](site/market.js#L375)) compute to roughly 2.9:1 and 3.4:1 against the 3:1 non-text line. The 11px chart axis ([site/style.css:8529-8534](site/style.css#L8529-L8534)) passes contrast but is the smallest type on the card. Finally, selecting a project is silent — `panel.replaceChildren(...)`, `panel.hidden = false`, `mapWrap.classList.add('panel-open')` with no live region and no `aria-expanded` on the row, `aria-current="true"` ([:557](site/devmap.js#L557)) being the only trace ([site/devmap.js:563-569](site/devmap.js#L563-L569)) — and the fix is the same `focus: true` change already named above, so it costs nothing extra.

## Test gaps, ranked by how quietly they fail — on top of an already strong check

**Say first what not to rebuild.** `backend/test/browser/devmap-check.mjs` is a genuinely strong correctness harness. Its best decision is an independently reimplemented expectation that deliberately does not import `site/market.js`, so a bug in `filterProjects` cannot hide. On top of that it audits the built data (every project has city/name/id, positive cost, ISO dates, paired lat/lng), checks every filter alone plus five named combinations against count, list length, drawn markers, pin text and the empty state together, verifies menu options match the data with counts, covers the legend end to end (counts sum to the shown total, hiding removes exactly its rows and pins, a hidden category keeps its count, re-showing restores), the chart (bar counts match filings per month, a bar click filters from that month on and a second clears), all three sort orders, the panel (pin click opens and highlights, two links, panel inside the map, close, next/prev in list order, Escape closes and returns focus to the row), `Clear all` resetting search/menus/legend/chart month/hiring together, the desktop tab order with a visible focus ring on every control, layout and no-sideways-scroll at phone width, the phone "Search & project list" button, smaller-filing pins and "Show on map", named regression anchors, and zero page errors per viewport ([:689](backend/test/browser/devmap-check.mjs#L689)). Two soft budgets do fail properly: search within 400ms ([:339](backend/test/browser/devmap-check.mjs#L339)) and "filter change paints within 150 ms" ([:355](backend/test/browser/devmap-check.mjs#L355)).

The gaps, ranked by quietness:

1. **The slow-phone block measures and never asserts.** [backend/test/browser/devmap-check.mjs:692-716](backend/test/browser/devmap-check.mjs#L692-L716) emits only `console.log` rows ([:693-695](backend/test/browser/devmap-check.mjs#L693-L695), [:715](backend/test/browser/devmap-check.mjs#L715)); the last `log()` call in the file is at [:689](backend/test/browser/devmap-check.mjs#L689), so `results` is untouched and `failed` ([:721](backend/test/browser/devmap-check.mjs#L721)) cannot be affected. 2. **The time-lapse — the newest feature — has no coverage whatsoever.** The check contains no match for `lapse`, `blip` or `keepView`. The only thing between a broken lapse and a green run is the `no page errors` assertion.

## Open questions where intent is not recoverable from code

Four decisions are not stated anywhere in the source, and each changes which fix is right.

**Are filters deliberately absent from the URL hash?** `writeMarketHash`/`readMarketHash` carry only `city, focus, sort, order, tool, compare` ([site/market.js:212-248](site/market.js#L212-L248)), while the map's filters, sort and hiring toggle are module globals. The comment on `filters` says they are "kept while the section redraws or the city changes", so cross-city persistence reads as intentional — but the consequence is the worst of both worlds: a filtered map is neither shareable nor reload-restorable, and arriving from a metro link inherits whatever the user last did on another metro, with "Clear all" visible and a count reading "12 of 3,480". Adding a few hash keys written with `replaceState` would fix sharing, reload and the cross-city leak at once and would let the entry cards link to a *clean* map. Whether that is wanted, or whether the globals are a deliberate "keep my working set" affordance, is a product call.

**Should the phone sheet be modal?** The code commits to neither: it is `position: absolute` with `z-index: 600` covering roughly 78% of the map, the filters and chart behind it are `display: none` ([site/style.css:8567-8569](site/style.css#L8567-L8569)), and there is no `role="dialog"`, no focus trap and no focus move. If it is meant to be modal, the fix is `aria-modal` plus a trap; if non-modal, the filters should stay reachable. **Should `sort` survive "Clear all"?** It currently does, invisibly; either reset it or exclude it deliberately and say so in the UI — but pick one. And **what is the intended relationship between the map search and the Smaller filings box below it?** The map search drives that box one-way with no consent and no clearing ([site/devmap.js:480](site/devmap.js#L480)); whether it should be a shared query, an independent one, or an explicit "search smaller filings too" affordance is a design decision, not a bug to patch blind.

Two further things cannot be settled without a running browser and should be confirmed in a `devmap-check` run rather than asserted: the 22%/28%/62% sheet-geometry mismatch, and the 820/900/640 breakpoint window. The repo's own `devmap-check` skill is the right harness for both.
